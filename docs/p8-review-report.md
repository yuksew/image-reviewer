## A. 設計の主張が成り立たない（必ず直す）

### A1. `review_group.kind` の語彙は `duplicates`（複数形）。設計の `duplicate` では 422 で**線 3 が通らない**

- 場所: §0.8 L131（`kind='duplicate'`）・§3.1 L415・**線 3 L280**（`POST /api/groups {kind:'duplicate', …}`）・§0.15 の 10 L254・§10-2 L638-639。専門文書 §2.2 も `duplicate`
- 根拠: `db.py:125` `CHECK (kind IN ('manual', 'request', 'duplicates', 'batch'))`。`review.py:254` `if kind not in ("manual", "request", "duplicates", "batch"): raise ReviewError(422, …)`。実データの `review_group` の DDL も同じ（実行 #1）
- 帰結: 線 3 を設計どおり打つと **422 `kind が不正です`**。§10-2「語彙に `duplicate` があるか要確認」は**もう答えが出ている**（`duplicates` ならある）
- 直し方: 設計の `duplicate` を全部 `duplicates` に。§10-2 と「サービス層で検査」の分岐は消す。**`review_group` は実データで 0 行**（L135 の「1 件」は古い）

### A2. `client_token` を `deletion_log` の**行**に置くと、一括削除で `ux_deletion_token` に当たる

- 場所: §2.1 L339（`client_token TEXT -- 再送の鍵（段 2・段 3）`）・L344-345（`CREATE UNIQUE INDEX ux_deletion_token ON deletion_log(client_token) WHERE client_token IS NOT NULL`）・§0.13 L200（**一括削除の実行にも付ける**）・§3.2 L423（`POST /api/locations/bulk-delete {preview_id, confirm, client_token?}`）・§8-3 L576
- 何が起きるか: 一括は **1 要求で最大 200 行**を `deletion_log` に書く。同じ `client_token` を各行に写すと **2 行目で UNIQUE 違反**（`IntegrityError` → 500。取引なら全体が巻き戻る）。写さなければ再送の守りが無い。§8-3 のテストは 1 件の再送しか見ないので**緑のまま**
- 直し方（推奨）: 再送の鍵は**要求の単位**に置く。`pending_delete_preview` の行を実行後に**消さず** `executed_at` / `result_json` / `client_token` を持たせる（同じ token の再送は `result_json` を返す）か、`delete_request(id, client_token UNIQUE, actor, result_json, at)` を 1 表足して `deletion_log.request_id` で紐付ける。**§4.3 の「実行すると行を消す」も改める**（消すなら台帳に写してから）。§8-3 は「**一括**で同じ token を 2 回」に直す

### A3. 段 3 で `asset_location` を消すと**取り消しで戻せない**（戻すのに要る列が台帳に無い）

- 場所: 専門 §3.1 の表「段 3: `asset_location` を消す」・P8 §4.1 L459-468（段 3 の DB は「`deletion_log` の段 3 の行」だけ）・専門 §3.4「`restored_at` を立てて **`asset_location` を復活させ**」・**線 6 L283**・§2.1 L319-350（`deletion_log` に `path` と `size` はあるが **`display_path` / `mtime_ns` / `is_primary` / `last_seen_at` が無い**）
- 根拠: `asset_location` の DDL は `path PK / display_path NOT NULL / asset_id / size NOT NULL / mtime_ns NOT NULL / is_primary / missing_at / last_seen_at NOT NULL`（`db.py:161-170`）。行を消した後に復活させるには **`display_path`（NOT NULL）と `is_primary`** が要るが台帳に無い。`mtime_ns` は戻した後に `stat` し直せるが、**「同じ内容か」の再照合（§0.7）の基準も失う**
- 帰結: 線 6「`undo` → 元のパスに戻る」が**設計の DDL では作れない**（実装者が列を発明する）。ついでに §6.3「段 3 は `review.json` に出る（`missing: true`）」も、行が無いと `missing` を導けない
- 直し方（推奨）: **窓の間は行を消さない**。段 3 の実行で `asset_location.missing_at` を立てる（既存の「参照切れ」と同じ意味。走査の `mark_missing` とも整合する）だけにし、**行を消すのは `remaining_sec <= 0` で保留領域を消すとき**。取り消しは `missing_at` を NULL に戻す。**`asset.deleted_at` は段 3 の実行で立てる**（窓の間も一覧には出ない＝§4.1 の「出ない」はそのまま。`missing_at` は「実体がどこにあるか」、`deleted_at` は「一覧に出すか」で役割が違う）。「最後の 1 つ」の判定は `missing_at IS NULL` の場所の数なので、窓の間に 2 枚目を消そうとすると正しく「最後の 1 つ」になる。§4.1 の表と §8 に「段 3 の直後も行がある」を足す

## B. 重大

### B1. 上限 200 が**人にも**効き、「失敗した大量生成をまとめて消す」が 201 枚から不可能

- 場所: §0.13 L199・§3.2 L422（preview で 422 `too_many`）・Q2 の帰結 (d) L226（「エージェントは一括の `preview` も使えるが、上限は同じ」）・§3.4 L450
- 何が起きるか: 専門文書 §3.1 が挙げる利用者の場面「失敗した大量生成をまとめて消す」「容量を空けたい」は 200 枚を超える。フォルダ単位の preview が 422 で止まり、**画面から消す手段が無い**（200 枚ずつ選び直させる）。Q2 の帰結 (d) は**エージェントの暴走**を止めるための上限で、人を止める理由が書かれていない
- 直し方（推奨。G1）: 上限は **`actor` ごと**に持つ。エージェントは 200（超えたら 1 枚も消さない。今のまま）。人は**上限なし**（preview が件数と合計バイトを見せるのが守り）か、設定値（既定 2,000）。§8-30/31 は「エージェントで 201」に直す

### B2. 日次スナップショットが「起動時」だけだと**動きっぱなしのアプリでは一度も取れない**。「いま取る」も同じ日なら取らない

- 場所: §0.12-1 L176（「日次スナップショットは起動時に 1 日 1 回」）・§3.3 L434（`POST /api/backup`「同じ日なら 200 で既存を返す」）・線 10 L287（「同じ日にもう一度押しても増えない」）
- 根拠: 利用者のアプリは 8790 で**立てっぱなし**（今回の指示書 §0 も「止めるな」）。起動時だけでは日をまたいでも取られない。「いま取る」が朝の自動の物を返すと、**1 日分の判断が入っていない物を「取れた」と見せる**
- 直し方: (1) 取るかどうかの判定を**窓のタイマー（30 秒）と同じ周期**で行う（「今日のフォルダが無ければ取る」。起動時は最初の 1 回）。(2) 「いま取る」は**必ず新しく取る**（`<YYYYMMDD>/` を一時フォルダに作って `os.replace` で差し替えるか、`<YYYYMMDD>-<HHMMSS>/`）。線 10 の「増えない」は**自動**の話に限る

### B3. 線 12「先頭 4 KB を壊す」では**開けない**。`quick_check` は結果を返さず**例外**を投げる

- 場所: 線 12 L289・§0.12-5 L187-188・§3.3 L437（`GET /api/health/db`）・§10-12 L653-654
- 根拠（実行 #5）: 先頭 4 KB → `sqlite3.DatabaseError: file is not a database`（接続はできるが最初の SQL で落ちる。**読み取り専用で起動して `quick_check` の結果を出す**ことができない）。2 ページ目を潰すと `PRAGMA quick_check` は **行を返さず `database disk image is malformed` を投げる**が、`asset` / `decision` / `settings` の `SELECT` は通る
- 帰結: 「`quick_check` の結果が出る」を `fetchall()` の中身で判定すると、**壊れた DB ほど例外で 500** になる（P6-1a の `actor` 語彙外 500 と同じ型）。線 12 の壊し方では「読み取り専用で起動」そのものが成り立たない
- 直し方: `quick_check` は **`try/except sqlite3.DatabaseError`** で受け、例外も「壊れている」に数える。線 12 は「**2 ページ目（4096〜8191 バイト）を 0 で潰す**」にする（開けるが壊れている）。先頭を壊した場合は別の線（「起動はするが `/api/health/db` が 503 と復元の案内を返し、他の口は 503」）。`db.connect(read_only=True)` は既にある（`db.py:71-91`）が、`Store` は `db.open_db(self.data_dir, check_same_thread=False)` で**書き込み用に開く**（`store.py:62`）ので、§10-12 の「読み取り専用で開く道」は `Store` 側に要る

### B4. 取り消しの「上書きしない」を `exists` → `os.replace` で作ると**上書きする**。Windows の `os.rename` が原子的に拒む

- 場所: §0.6-4 L107-108・専門 §3.4「`os.path.exists` を `os.replace` の直前に確かめる（完全な原子的保証はしない。未確認）」・§8-11 L584・線 6 L283
- 根拠（実行 #4）: `os.replace(a, b)` は **b が在っても黙って上書き**した。`os.rename(held, orig)` は orig が在ると **`FileExistsError`（WinError 183）** で止まり、orig は無傷。Windows では `os.rename` が `MoveFileExW` を `MOVEFILE_REPLACE_EXISTING` 無しで呼ぶので、**検査と置き換えの間の競合が無い**
- 直し方: 取り消しの復帰は **`os.rename`**（`FileExistsError` を `409 target_exists` に写す）。`exists` の事前検査は要らない。§8-11 は「`os.rename` を `os.replace` に替えると、元の場所の別のファイルが壊れる」で**決定的に**書ける（競合を作らなくてよい）。段 3 の保留領域への移動は `os.replace` のままでよい（移動先は自分が作る空フォルダ）。あわせて線 6 の「別名で戻る（`… (1).png`）」と §3.2 L425 の「`409 target_exists` → `?as_copy=1`」が**食い違う**（線 6 は自動で別名、API は 409 で止める）。API の方（止めて尋ねる）に揃え、別名は専門 §3.3 の `<名前>.<連番>.<拡張子>` に統一する
