## 1. 守ること

1. **`docs/p5-review-report.md` 以外のファイルを変更しない。** 直したくなっても提案として書く。
2. **コードを書かない。** 設計の妥当性だけを見る。
3. **称賛は要らない。** 問題と根拠だけ。
4. **推測で断定しない。** 文書に無いことは「書かれていない」と指摘する。
5. **実行して確かめられない**（この環境では `rg` の起動が拒否されるため `Glob`/`Grep` も使えない）。
   `Read` で個別に読むこと。**算術や仕様の確認を「記憶」で断定しない**（前回の点検で
   「Windows の挙動は記憶に基づく」と自分で申告した部分がある）。

## 2. この段は何か

`design.md` §14 の工程 **P5**。順序は点検 G11 で「**P5 を先に**」と決まっている（判断がこの道具の主目的）。
P5 は **判断（キープ / ボツ）と比較**を作る段で、次の 4 つが入る:

1. 判断の台帳（追記のみ）と、`asset` への現在値の写し
2. 1 枚の判断と、**まとまりから 1 枚選ぶ / 全部ボツ**
3. 比較（並べる / 来歴の差分表 / 差分ヒートマップ / 同期ズーム / 似ている順）
4. 他ツールが読む `review.json` の書き出し

**この段では作らない**: 要求（P6）、注記（P6）、タグと語釈（P4）、条件の記録（P7）、重複と削除（P8）、
監視（P3）。

## 3. すでに確定していて、覆せないこと

設計は 2 回の点検を受け、次は**利用者が承認済み**です。**これに反する設計は「矛盾」として指摘**してください。

**判断**
- 言葉は **キープ / ボツ**（契約値は `kept` / `rejected` / `unreviewed`、verdict は `keep` / `reject` / `clear`）
- 「採用」＝**気に入ったもの**（作品で使うかは別）。軸は 1 つ。**点数（星）は入れない**
- 判断の単位は 1 枚ずつとまとまりの**両方**。**まとまりの枚数に上限を置かない**
- **エージェントは判断を書けない**（`POST /api/reviews` と `decide` は `human` 以外 **403**）。
  入口は要求の `ai_pick` だけ（点検 A5）
- **自動でキープにしない**。AI の下書きは人が確定する
- ボツには理由を付ける（理由マスタは利用者が編集。**「同じまとまりに良いものがある」は入れない**）
- 画像への**手動タグ付けは残す**（語の統合・改名だけを作らない。点検 G1）
- キーボードは**補助**。キーが無いとできない操作を作らない

**書き出し**
- 判断のたびに書くのは**影響したまとまりのファイルだけ**。全件は手動と日次（点検 B4）
- `tags` / `prompts` は**既定で出さない**（`include_tags` / `include_prompts`）
- **決定性の確認は `generated_at` を除いて**行う
- 契約は `schemas/review-export.schema.json`（`abi 0.1`）。`kind`（生成物 / 参考資料 / 写真）を出す

**安全**
- 削除は 3 段階。実削除は**5 分間取り消せる**（**アプリが動いていた時間**で数える）
- 触ってよいのは **`asset_location` に実在するパスそのものだけ**（完全一致）
- Host / Origin / Content-Type を検査する（同一オリジン配信なので画面は通る）

### 5.2 とくに厳しく見てほしいところ

1. **`store.json`（1 ファイル）に台帳を載せる是非。** プロトタイプは 263 枚で 600 KB。
   判断のたびに書き直すと §8 の「100ms」が守れるのか。**SQLite へ移すのをこの段に含めるべきか**、
   それとも P5 は JSON のまま進めて P6 以降で移すべきか。**あなたの判断と根拠**を書いてほしい。
2. **「影響したまとまり」の定義。** 1 枚の判断でも、その画像が複数のまとまりに入っていれば
   複数のファイルを書き直すことになる。**どこまでを 1 回の書き出しに含めるか**が曖昧でないか。
3. **書き出しの遅延（2 秒）と、落ちたときの取りこぼし。**
   `decision.created_at > export の mtime` という判定だけで足りるか。
   **時計のずれ・同時刻・複数のまとまり**で漏れないか。
4. **全部ボツのときの枚ごとの理由。** 「まとまりの理由を写す」と「後から直せる」が、
   §3.2 の「枚ごとに理由が必須」と噛み合っているか。**8 枚ぶんの理由を選ばされる**ことにならないか。
5. **`decided` の後に判断が入ったら `open` に戻す**規則が、§3.1（1 枚の判断）からも働くか。
   §3.2 は `decide` の話しかしていない。
6. **差分表の鍵の列挙。** `llm` は入っているが、`init_image`（img2img の元画像）・制御入力
   （ControlNet など）・`clip_skip` が抜けていないか。**プロトタイプが実際に読んでいる鍵**と突き合わせること
   （`src/image_reviewer/png_meta.py` の `analyze_graph` が返す鍵）。
7. **pHash の実装可能性。** Pillow だけで（追加の依存を入れずに）実装する前提が成り立つか。
   DCT を numpy で書く前提は妥当か、それとも別の手段が要るか。
8. **§7 のテスト 26 件**で、**この段に要らないもの**と、**今すぐ要るのに無いもの**。
9. **P5 の範囲**に、落としているもの・入れすぎているものはないか。
   とくに「比較の 5 つの見方を全部この段で作る」ことの是非。

## 6. 報告の形式

`docs/p5-review-report.md` に:

```markdown
# P5 設計の点検報告

- 点検した版 / 総合判定: 実装に進んでよい / 修正してから進む / 設計をやり直す

## A. 決定との矛盾（必ず直す）
## B. 重大な問題（設計を変える必要がある）
## C. 中程度（実装前に決めたい）
## D. 軽微（実装中でよい）
## E. 事実・前提の誤り
## F. 未確認のまま危険な箇所
## G. 依頼者への質問（判断が要るもの）
## H. 私が見落としている観点
## I. §11 の 12 の問いへの回答（1 件 1 行以上）
```

- 各項目に**必ず「場所」**（ファイルと節）。
- 「なぜ困るか」は**実装が始まった後で気づいたときに何が起きるか**で書く。
- **問題が無いと判断した観点は「見た結果、問題なし」と 1 行で書く**（見落としと区別するため）。

最後に、**最も重大な 3 件**を理由 2〜3 文で。
そのうち少なくとも 1 件は、**P5 の設計を書いた者が気づいていないもの**にしてください。
