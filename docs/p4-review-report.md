## A. 設計の主張が成り立たない（必ず直す）

### A-1. §0.7（108-111 行）「`(` `)` `[` `]` `:` と `\` は語に含めない」が CSV の語名を壊す

- **現物**: `wd-eva02-large-tagger-v3.csv`（10,861 行）のうち **括弧を含む語 1,596**（general 204 / character **1,392 = キャラ名 2,751 の 51%**）、**コロンを含む語 41**（`:d` `:o` `:3` …）。`[` を含む語は 0。設計の正規化を CSV 自身に当てると **1,619 語が別の文字列に変わる**（`norm_check.py`）。
- **ノードの出力**: `wd14tagger.py:97` は `(`→`\(`、`)`→`\)` にエスケープして返す。実行で確認: `character_threshold=0` で投げると `admiral_\(kancolle\)` / `2b_\(nier:automata\)` / `rem_\(re:zero\)` が返る（`wd14_paren.out.txt`、括弧を含む語 1,391）。
- **帰結**: 設計の正規化を通すと `admiral_\(kancolle\)` → `admiral_kancolle` で**語彙に無い**。§0.8-4「CSV の語彙に一致するものだけ採る」なら PNG の語からキャラ名が全部落ち、§1.2 の線 8（集合の一致）は方式の差でないのに差が出る。`:d`（笑顔の記号）など 41 語も消える。
- **直し方**: 正規化は「前後の空白を落とす → 空白を `_` → 小文字 → **`\(` `\)` のエスケープを外す**」まで。**括弧とコロンは語の一部として残す**。落とすのは **PNG の断片の外側の重み `( … :1.5)` だけ**（§0.8-2 の「重みと括弧を外し」も「**外側の 1 組と `:数字` だけ**」に限定する）。`[` `]` は CSV に無いので落として構わない。
- 場所: 108-111 行、129 行、§8.1 の 8（626 行。`three_quarter_view` が出ることだけでは足りない。**`star_(symbol)` が壊れない**ことを足す）。

### A-2. §0.5（68-84 行）ComfyUI 経由は「画像をどう渡すか」が無く、実データはそのままでは食わせられない

### A-3. §0.9（153-163 行）・線 6（248 行）・§8.1-9（627 行）「行数が一致したら位置で対応させて保存」は、**行数が一致しても対応が合わない**

### A-4. §7（591-593 行）「`WD14Tagger|pysssss` 定常 0.40 s/枚」と「10,000 枚で約 67 分」は**キャッシュの値**

- `comfy_distinct.py`: **別々の 6 枚**を順に投げると **3.37 / 2.88 / 2.80 / 2.79 / 3.09 / 2.86 s**。同じ 6 枚をもう一度投げても 2.78〜3.10 s。**直前と同じ画像を再投入したときだけ 0.22 s** で、`/history` の `status.messages` に **`execution_cached`** が出る（= 実行していない）。
- 最も確からしい原因は `wd14tagger.py:58`: **呼ばれるたびに `InferenceSession(...)` を作り直す**（1.2 GB の ONNX を毎回読む。私の計測で session の作成は 2.0〜2.3 s、1 枚目の推論 0.44 s で、足すとほぼ 2.9 s になる）。ComfyUI の中で切り分けてはいない（確かめ方: ノードにセッションの持ち回りを足して測る）。セッションを持ち回る `IllustTagger`（`_sessions` 辞書）は **0.26〜0.31 s/枚**（別々の 6 枚）。
- **見積りの直し**: 10,000 枚は `WD14Tagger` で **約 8 時間**、`IllustTagger` で **約 45 分**、**内蔵（GPU）で約 11 分**（0.063 s/枚＋読み込み。§C-1）。`design.md` §8.2 の「0.5 秒/枚・1 万枚 1.5 時間」を満たすのは **`IllustTagger` と内蔵だけ**。
- **直し方**: §0.5 の既定を **`IllustTagger`** にする（スコアも返る。§B-1）か、内蔵を既定にする。`WD14Tagger` は「スコアが無く遅い」と書いて選択肢に残す。§7 の表は「**別々の画像で測った**値」に差し替える（測り方を「同じ画像を 3 回」から「別々の画像を N 枚」に直す。§H の表に私の値がある）。

## B. 重大

### B-1. `WD14Tagger|pysssss` は**スコアを返さない**。既定の方式だと `asset_tag.score` が全部 `NULL`
- 実行: 出力は `outputs["2"]["tags"]` の **1 要素・カンマ区切りの文字列だけ**（748 文字・66 語）。スコアを含む鍵は無い。
- 設計は §3.4（441 行）で `source='wd14'` に `score: 0.9931` を例示し、§0.10（176 行）で「`score` の降順」に並べ、§2.4 で「スコアはタガーの行のもの」を出す。**既定の経路ではこれが全部空**になる。
- `IllustTagger` は `round(p, 4)` で **4 桁に丸めて**返す（`illust_tagger/__init__.py:96`）。§0.10（177 行）の「`score` は REAL のまま丸めない」は**ノードの外では守れない**。内蔵だけが float32 の生の値を持つ。
- 直し方: 既定を `IllustTagger` か内蔵にし、「`WD14Tagger` を選ぶとスコアは無い」と §0.5 に書く。「丸めない」は「**受け取った値をそのまま入れる**（IllustTagger は 4 桁）」に直す。

### B-2. `onnxruntime-gpu` は**黙って CPU に落ちる**。§0.4（65-66 行）の「どちらを入れたか」では足りない
- 実行: ComfyUI 同梱の `python_embeded` で `InferenceSession(..., providers=["CUDAExecutionProvider", "CPUExecutionProvider"])` を作ると、**`get_providers()` は `['CPUExecutionProvider']` だけ**（CUDA の DLL が読めず、例外なしで落ちる）。先に `import torch` をすると `['CUDAExecutionProvider', 'CPUExecutionProvider']` になり **0.063 s/枚**（CPU は **0.75 s/枚**。12 倍）。
- `doctor` の 1 行は「GPU 版を入れた」ではなく **`session.get_providers()[0]` の実際の値**を出す。内蔵で CUDA を使うなら、**CUDA / cuDNN の DLL を自分で用意する**（`onnxruntime-gpu` のホイールには入っていない）ことを §0.4 と §10-2 に書く。`uv sync --extra tagger` だけでは GPU にならない。

### B-3. `POST /api/tags/gloss`（§3.5）は「冪等ではない（訳す）」のに再送の守りが無い
- §0.10（175 行）は「口が冪等なので `client_token` は使わない」と書くが、`POST /api/tags/gloss` は模型を回す（2.5〜10 秒）。画面の二度押し・再送で**同じ語を 2 回訳す**。`edited=0` の語は上書きされる（規則どおりだが無駄）。
- 直し方: **「語釈の無い語だけ訳す」を既定にする**（`force=false` なら `tag_gloss` に行がある語は飛ばす）。これで 2 回目は 0 回の呼び出しになり、`client_token` 無しで足りる。§3.5 の表に「既に語釈がある語 → `skipped`」の行を足す。

### B-4. PNG の語（§0.8）の採用率は **46%**。設計の例 `three quarter view` は**語彙に無い**
- `norm_check.py`（実データ、`final_prompt` のある **180 枚**。設計は 183 と書くが dict の meta は 183、`final_prompt` が空でないのは 180）: 断片 4,964 → **採用 2,259（46%）／落ちる 2,705（54%）**。1 枚あたり採用 12.6・落ちる 15.0。
- 落ちる断片の上位: `masterpiece`（180）、`best_quality`（180）、`safe`（180）、`score_7`（170）、**`three_quarter_view`（68。語彙に無い）**、`adult_woman`（60）、`slender`、`handsome`、`clean-shaven` …。品質語と自然文が大半で、**設計 §0.8 の判断（既知語だけ）は妥当**。ただし §0.8 の例（129 行）と §8.1-8（626 行）は `three_quarter_view` を「出る語」のように書いており、**この語は採られない**。例を `looking_at_phone`（語彙にある）などに変える。
- `,` に加えて `.` でも割り、`First girl:` / `Second boy:` の前置きを外すと **49%**（`black hair` などが拾える）。採るかは §G-4。

### B-5. §8.1-18（636 行）「契約の `gloss` を実際に出す」は、語釈が 1 語も無い状態では落ちない
- `include_tags=true` でも `tag_gloss` が空なら `gloss` は `null` で通る。テストは「**語釈を 1 語付けてから出し、その語の `gloss` が値を持つ**」まで書く（P6-0 の B1 と同じ型）。線 4・5 のテストと組み合わせれば足りる。

- **ただし値が古くなる経路がある**（実行で確認）: CSV が無い環境（§0.8 の「`known` を全部 0 にする」）や、PNG の切り出しが**先に** `black_hair` を `known=0` で入れたあと、WD14 が同じ語を付けるとき **`INSERT OR IGNORE` だと `known=0` と `category=NULL` のまま残る**（語彙にある語なのに `known=0`、見出しも出ない）。
  - **直し方（必須）**: `known` は「**`name` が語彙にあるか**」の**導出値**と決め、書き方を **`INSERT … ON CONFLICT(name) DO UPDATE SET known = max(known, excluded.known), category = coalesce(excluded.category, category), …`** にする（実行で `(1, 0)` に直った）。さらに**ジョブの最初に 1 文で引き直す**（`UPDATE tag SET known = (name IN vocab)`。3,154 行 × 10,861 語で **1 ms**）。これで CSV が後から入った環境も、モデル（CSV）を変えた環境も正しくなる。
  - §2.1 の `known` に **`CHECK (known IN (0, 1))`** を足す（§0.10 の「語彙は DB でも守る」と同じ型）。
- **`known` はどの語彙に対してか**: 設計は「CSV 10,861 語」と書くが、タガーのモデルを変えれば CSV も変わる（`wd-vit-tagger-v3` などは語彙が少し違う）。「**設定のモデルの CSV**」と明記し、モデルを変えたら引き直す（上の 1 文で足りる）。
- **§0.7 の括弧落とし（本文 A-1）があると `known` が狂う**: `admiral_\(kancolle\)` も PNG の `admiral (kancolle)` も `admiral_kancolle` になり、語彙に無いので **`known=0`**。しかも CSV 自身を同じ正規化に通すと **5 組が衝突**（`:d` と `d:` → `d`、`:3` と `3:` → `3`、`;)` と `;(` → `;`、`:>` `>:)` `>:(` → `>`）。**A-1 を直さない限り `known` は正しく付かない**。

### I-2. `known=0` の語がタグ検索を汚さないか（指示の 1 つ目）

実データ 180 枚に §0.8-4 をそのまま当てると:

| 何 | 値 |
| --- | --- |
