## 0. 拘束力のある差分（本文と食い違う点・本文が黙っている点）

### 0.1 段の分け方と合格の線

### 0.4 **完全重複はこの実データでは空振り。本体は準重複**（**実測**）

| 種類 | 定義 | **実データ（263 枚）** |
| --- | --- | --- |
| 完全重複 | 同じ `sha256` が 2 か所以上（`asset_location` が 2 行以上） | **0 群**（263 枚すべて 1 か所） |
| **準重複** | pHash のハミング距離 **≤ 6** | **21 群 / 57 枚**（2 枚が 10 群・3 枚が 7 群・4 枚が 4 群） |
| ほぼ同じ絵 | 距離 **≤ 3** | 17 群 / 39 枚（**距離 0 が 9 組**） |
| 同じ生成条件 | `meta` の `seed` が同じ | 19 群（**最大 31 枚**。**要確認**＝バッチ生成の可能性。§10） |

- **完全重複の検出は実装するが、この環境では 0 件**。画面は**空のときに「完全重複はありません」と 1 行出す**
  （**空の一覧を黙って出すと「壊れている」と思われる**）。
- **準重複が本体**。実例（§1.3）: 1024×1024 が 4 枚（サイズが 1179/1183/1138/1166 KB）＝**同じ絵の別ファイル**、
  1024/1536/2048 の 3 枚＝**リサイズ違い**。**専門文書 §2.2 の 2 種類が実データにある。**
- **`asset.sha256` の `UNIQUE` があるので「同じ中身の 2 行」は構造的に作れない**（専門 §2.1）。
  つまり**完全重複は「同じ絵を 2 か所に置いた」ときだけ**出る。**この使い方は今の利用者には無い**（1 か所しか置いていない）。

### 0.5 pHash は**全件計算が要る**（実測: 14.8 ms/枚）

- 実データで **pHash が入っているのは 91 / 263 枚**（P5-3 はサムネイルを作る復号に同居して入れる＝
  **見た画像から入る**）。**未計算の 172 枚を計算するのに 2.6 秒**（14.8 ms/枚・**復号込み**。私の実測）。
  → **1 万枚なら約 2.5 分**（**（点検 D3）`comparison.md:283` に「復号＋両ハッシュで 14.1 ms/枚」が既にある**ので、
  **この段の実測（14.0〜14.8 ms/枚）は既存の実測の追認**。**`comparison.md` §7 の「8 ms/枚・2 分以内」は復号を含まない見積り**だった）。
- **だから `GET` では計算しない**（家風: `GET` は 1 バイトも書かない。§0.13）。
  **`POST /api/duplicates/compute`（背景ジョブ）で足りない分を計算**し、`GET /api/duplicates/near` は
  **計算済みの物だけ**から候補を返す。**未計算の枚数**を応答に出す（例: `"unhashed": 172`）。
- **`phash_band` は `asset.phash` が入ったときに一緒に書く**。**（P8-1 の監査 C-3 / E-2）書き手は `store.set_hashes` の 1 か所**（前の版は「`compare.capture_hashes` / `ensure_hashes` の
  隣に 1 手足す）。**帯の値は 16 進 2 文字**（専門 §1.3）。

### 0.6 削除の 3 段階と 5 分の窓（**「アプリが動いていた時間」で数える**）

専門文書 §3.1・§3.4 のとおり。**この段で特に守る 9 点**（**7〜9 は P8-2 の監査で足した**）:

1. **段 3 は即座に unlink しない。** **同じボリューム**の `<data>/pending-delete/<削除ID>/` へ **`os.rename`** で移す
   （**名前の付け替えなので一瞬**。**（監査 D-16）`os.replace` ではない**——`os.replace` は在ると黙って上書きする）。
   **（監査 B-1）台帳の 1 行を先に書いてから動かす。動かせなければ行を消す**（逆順だと、取引が失敗したときに
   ファイルだけが移り、**台帳にも要求にも残らない迷子**になって一覧には「在る」と出続ける）。
2. **窓は `remaining_sec` を単調時計で減らして数える**（**壁時計では数えない**）。30 秒ごとに前回からの経過を引く。
   **スリープ・休止・終了の間は進まない**。**`purge_at` は画面に出す目安の壁時計時刻**で、
   **自動削除の判定には使わない**（専門 §3.4 の点検の誤りをそのまま守る）。
   **引くのは `min(前回の周期からの経過, その行が生まれてからの経過)`**（消した直後の周期で「消す前の時間」まで
   引かない。実機で 35 秒に 60 秒ぶん引かれた）。**1 秒に満たない端数は次の周期に繰り越す**
   （**（監査 D-11）切り捨ては窓が延びる側に倒れる**）。
3. **起動時には絶対に消さない。** 残り時間を引き継いで「最近の削除」に戻し、タイマーを張り直す。
   **`purge_at IS NULL` の行（戻せなかった物）はタイマーの対象にしない**。
   **（監査 B-1）台帳を先に書く順で「移動の前に落ちた行」が残りうる**: 保留の実体が無い行は、
   元の場所にファイルが在れば**戻したことにする**（削除は起きていない）し、どちらにも無ければ
   **後始末を完了する**（前の周期の実削除が DB の前に落ちた形）。**台帳に無い `pending-delete/` の中身は
   「拾い物」として起動時に警告へ出し、`GET /api/pending-deletes` の `found` にも出す**（**消しも動かしもしない**）。
4. **（点検 B4）取り消しは元のパスを上書きしない。** **`os.rename` を使う**（Windows は `MoveFileExW` を
   `MOVEFILE_REPLACE_EXISTING` 無しで呼ぶので、**検査と置き換えの間の競合が無い**。
   `os.replace` は**在っても黙って上書きする**＝実測。`exists` の事前検査は**要らない**）。
   埋まっていたら **`FileExistsError`（WinError 183）→ `409 target_exists` で止めて尋ねる**
   （**（点検 B4・D4）API も画面も「止めて尋ねる」で揃える**。**`?as_copy=1` のようなクエリは使わない** —
   **本文の欄 `as_copy: true`** を送り直す形にし、**人だけが送れる**（エージェントは **403 `human_only`**）。
   別名は専門 §3.3 の **`<名前>.<連番>.<拡張子>`** に統一する）。
   **（監査 B-2）失敗したら `purge_at` を `NULL` にして自動削除から外す**——**`target_exists` だけでなく
   `move_failed`（元のフォルダが無い・別プロセスが掴んでいる）も同じ**。片方だけだと、409 を見た利用者の
   画面が「あと N 分」のまま進み、**窓が尽きたときに黙って消える**（専門 §3.4 の字義）。
5. **（Q2 の帰結 c・d／点検 B1）エージェントの削除も同じ窓で数える。** 誰が消したかで**窓の長さを変えない**。
   **`deletion_log.actor` に `human` / `agent` を必ず入れる**。**1 回の要求で消す枚数の上限は `actor` ごと**:
   **エージェントは 200**（超えたら **422 `too_many` で 1 枚も消さない**。一括の `preview` も同じ）、
   **人は上限なし**（**preview が件数と合計バイトを見せるのが守り**。専門文書 §3.1 の「失敗した大量生成をまとめて消す」
   「容量を空けたい」は 200 枚を超えるので、**人を止める理由が無い**）。
6. **（点検 B7・G5）段 3 を許すかは `root` ごと。** `root` に**「段 3 を許す」印**を持ち、**印が無い root は段 1・2 まで**
   （**409 `stage_not_allowed`**）。**既定は印なし**（実データの 262 / 263 枚は `c:\work\illust-authoring\.store\anima-dev` にあり、
   **別のツールの管理下**なので、勝手に実削除しない）。**どの root にも入っていない場所も許さない**（安全側）。
7. **（監査 B-3）実削除は錠の下で行う。** **`tick` と `_purge_expired` は `self._lock` を取る**
   （`undo` / `purge_now` / 一括は既に取っている）。取らないと、**窓の最後の周期**で `undo` と競合し、
   **ファイルは元の場所に在るのに `asset_location` の行が消え、台帳は『削除済み』**になる
   （監査が `threading.Event` で決定的に再現した）。**消す直前に行をもう一度読み、取引の中でも
   `UPDATE … WHERE restored_at IS NULL` の `rowcount` を見る**（二重の守り）。
8. **（監査 C-3・G-7）`asset.deleted_at` は資産の単位・削除は場所の単位。** 印を立てるのは
   **生きている `asset_location` が 0** になったときと、**生きた段 1 の行がある**ときだけ。
   **場所が 2 つある画像の片方を消しただけで一覧から消さない**（実削除の後も同じ）。段 1 は**場所ごと**なので、
   **同じ場所を 2 回外しても行を増やさない**（増やすと 1 回戻しても隠れたままになる）。
9. **（監査 C-2・G-6）保留領域を消す前に読み取り専用の属性を外す**（`S_IWRITE`。**自分の保留領域の中だけ**）。
   付いたままだと Windows の `unlink` が `WinError 5` で失敗し、**30 秒ごとに同じ警告を出してやり直し続ける**。
   **消せなかったら「いま消す」は 409 `purge_failed`**（500 にしない）。**保留領域そのものは消さない**
   （深さ 1 の `<削除ID>/` と深さ 2 のファイルだけ。`is_under(root, root)` は True なので、見ないと
   `rmtree` が**他の保留を巻き込む**）。

- **別ボリュームのときの保留領域**（専門 §7-6 の未確認）: **既定は `<data>/pending-delete/`**。
  **同じボリュームでない場合は「段 3 を断る」**（`409 cross_volume`）ことを**この段の決定**とする。
  理由: 別ボリュームへ移すと**コピーになり、大きいファイルで待たされ、途中で失敗すると中途半端**になる
  （専門 §3.4 が禁じている）。**安全側に倒して「いまはできない」と言う**方が、壊れるより良い。
  **画面には理由と対処（エクスプローラで消す）を出す。**

### 0.7 一括削除は**凍結 → 実行**（10 分で失効）

専門文書 §3.5 のとおり。**この段の決定**:

- 凍結は **DB の `pending_delete_preview`** に持つ（§0.3）。
- **実行の直前に 1 件ずつ `(size, mtime_ns)` を再照合**し、食い違った項目は **`skipped` にして残りは消す**。
  **（監査 C-5）比べる相手は「凍結した値」と「`asset_location` の行（＝実ファイル）」の両方**
  （凍結の値を見ないなら凍結に入れる意味が無い）。
- **`preview_id` は既定 10 分で失効**。失効したら**何も消さず `409 preview_expired`**。
  **失効してすぐは消さない**（409 を確かめられなくなる）が、**未実行で 1 日過ぎた行はタイマーが掃除する**
  （**（監査 G-5・D-10）`PREVIEW_KEEP_SEC`**）。実行済みの行は `result_json` を返すために残す（§4.3）。
- **（監査 D-2）段 3 の preview は `not_allowed`（`root.allow_stage3 = 0` の枚）も返す**
  （「消えます」と見せて実行で初めて `stage_not_allowed` になる形を作らない）。
- **`stage` は 1 / 2 / 3 の整数だけ**（**（監査 D-6）`true` は 422**。`int(True)` は 1 になり、
  確認のつもりで送った人が段 1 を実行してしまう。`3.9` も 422＝丸めない）。
- **（監査 D-14）`folder` の `scope` は登録した `root` の下だけ**（見ないと `C:\` の指定で
  管理下でない物まで凍結の一覧に入る。人に上限が無いので、preview が現実的な歯止めになる）。
- **`frees`（何がいつ空くか）**: 段 1 は 0（カタログから外すだけ）／段 2 はゴミ箱の掃除まで空かない／
  段 3 は**5 分の窓が過ぎた時点**。**画面にこの 3 つを出す**（「消したのに空きが増えない」と思わせない）。
  **（監査 D-9）preview の `frees.at` は `null`**（実行前は「いつ空くか」が決まらない。凍結の失効時刻は
  「窓が過ぎた時点」ではない）。実行の応答は窓の後の時刻を出す。
- **（監査 C-4）`confirm_last_copy` が要るのは段 3 の一括だけ**（段 1・2 は内容が失われない。
  実データは全枚が最後の 1 つなので、段 1 の一括まで毎回重い確認になっていた）。

### 0.8 重複の整理は**既存のまとまりレビューを使う**（専用の画面を作らない）

専門文書 §2.2 の決定。**`review_group` に `kind='duplicates'` / `policy='pick_one'` のまとまりを作り**（**（点検 A1）語彙は `duplicates`（複数形）。`db.py:125` の `CHECK` と `review.py:254` の検査が正**。
`duplicate`（単数）で送ると **422 で線 3 が通らない**）、
**既存の「まとまりレビュー」の画面で 1 枚選ぶ / 全部ボツ / 保留**ができる（P5-1 で作ってある）。
**重複専用の概念を増やさない。**

- **（点検 A1）実データの `review_group` は 0 行**（前の版の「1 件」は誤り）。**語彙には `duplicates` がある**ので**サービス層の分岐は要らない**（`CHECK` はそのまま。**表を作り直さない**）。
- まとまりの作成は**人が押したときだけ**（**自動でまとめない**。専門 §2.4）。

### 0.9 代表の選び方（**設計者が決めた**）

専門文書は「代表を 1 つ選んで他を外す」と言うが、**どれを代表にするかの規則を書いていない**。決める:

| 優先 | 規則 | 理由 |
| --- | --- | --- |
| 1 | **人が選んだ物**（`decision` が `keep`） | 人の判断が最優先 |
| 2 | **画素数が最大**の物 | リサイズ違いなら**元の解像度**を残す |
| 3 | **ファイルが大きい**物 | 画素数が同じなら情報量が多い |
| 4 | **（点検 C2・G3）`asset_location.mtime_ns` が新しい**物 | **規則 4 の `first_seen_at` は効かない**（全 263 枚が同じ分＝1 回の走査で入った）。**同じ寸法の作り直し（19 群）では「最終版」が新しい**ので、**新しい方**を推す（目視で「吹き出しを足した版」「水しぶきを直した版」が新しい） |
| 5 | `id` の昇順 | **決定的にする**（同じ入力なら同じ答え） |

- **画面には「おすすめ」として出すだけ**。**自動では外さない**（専門 §2.4）。
- **`GET /api/duplicates/near` の各群に `suggested_id` と `reason`（どの規則で選んだか）を入れる**（規則を 1 か所に持つ。**点検 C2**）。
  **画面で「古い方を推す」に切り替えられる**ようにする（どちらを残したいかは利用者次第）。

### 0.10 誤検出と除外（**解除できること**）

専門文書 §2.4・§3.1 のとおり。**`duplicate_exclusion` は `(小さい方, 大きい方)` に正規化**し、
**`CHECK (a_id < b_id)`** で機械的に守る。**`DELETE /api/duplicates/exclude` を必ず用意**（解除）。

- **除外した組は候補に出さない**が、**`deletion_log` には書かない**（除外の解除で行が消えるので、
  「いつ誰が除外したか」は `duplicate_exclusion` の行そのものが持つ。専門 §3.1 の注記）。

### 0.11 再リンク（**中身を確かめてから繋ぐ**）

専門文書 §4 のとおり。**新しい仕組みは作らない**（`asset_location.missing_at` と `location_history` は既にある）。

- 手段は 3 つ: **近くを探す**（同じルート内をファイル名で探し、**ハッシュが一致すれば繋ぐ**）／
  **場所を指定**（ファイル選択。**ハッシュを確かめてから**）／**自動**（走査のたびに一致する新規ファイルを繋ぐ）。
- **中身が違えば繋がない**（`sha256` の一致を必須にする）。**`size` と `mtime_ns` は見ない**
  （移動で mtime は変わりうる。**中身のハッシュが正**）。
- `location_history` に「入れ替わった」「繋ぎ直した」を残す（**既存の表を使う**）。

### 0.12 バックアップ（**`<data>` の外に置く**）

専門文書 §5 のとおり。**この段の決定**:

1. **日次スナップショットは起動時に 1 日 1 回**（同じ日に既に取っていれば何もしない）。
   `sqlite3.Connection.backup()` で DB を取り、**`sidecar/` と `export/` も同じスナップショットに入れる**
   （**`sidecar/` は PNG から取り直せない唯一のもの**。実データに **1 ファイル**あった）。
   **画像とサムネイルは入れない**（参照モードでは画像は利用者の資産。`thumbs` は 297 ファイルあるが再生成できる）。
   **（P8-4 の監査 D-9）出来るのは 5 つ**（`db.sqlite3`・`sidecar/`・`export/`・`settings.json`・`manifest.json`）。
   `settings.json` は**契約の `includes` に欄が無い**（`additionalProperties: false`）ので manifest では宣言しない。
2. **置き場の既定は `<data>` の外**: `%USERPROFILE%\image-reviewer-backups\<YYYYMMDD>\`
   （設定 `backup_dir`・環境変数 `IMAGE_REVIEWER_BACKUP_DIR`）。
   **理由**: `<data>` を消したときに備える対策を `<data>` の中に置くと**論理が閉じない**（専門 §5.1 の注記）。
   **（P8-4 の監査 D-11）置き場の値はその場で形を見る**（相対パス・ファイル・無いドライブは **422 `bad_backup_dir`**。
   次の周期の `last_error` 任せにしない）。**`--out` で指定した一時の置き場では古い世代を掃除しない**（D-6）。
3. **直近 7 個を残す**。`manifest.json` に**版・件数・作った時刻・含めた範囲**を書く。
   **掃除の対象は「自分の名前で `manifest.json` を持つ物」だけ**（`list_snapshots` は `prunable` でそれを言う。D-6）。
4. **CLI**: `image-reviewer backup --out <dir> [--include-library]` / `image-reviewer restore <dir> [--force]` /
   **`image-reviewer rebuild-metadata`**（PNG と sidecar から来歴を組み直す。**既存の `capture.py` の
   `write_sidecar` の形を使う**）。**`rebuild-metadata` は P8 で作る**（専門 §5.2 の 4 の約束）。
   **（P8-4 の監査 C-1）`restore` は取り出す前に manifest の `db_sha256` を照合する**（違えば **409 `bad_backup`**、
   `--force` で進む）。**（C-2）置き換えは「一時名に写して `os.replace` → その後に `-wal` / `-shm` を消す」**。
   **掴まれていれば何も壊さずに** 409 `restore_failed` の 1 行（トレースバックを出さない）。
   **（D-3）退避（`pre-restore-*`）は `backup_dir` を渡したときはそこ、渡さなければスナップショットの隣**
   （CLI は渡さない＝USB の写しから戻すと退避も USB）。
5. **健全性**: 起動時 `PRAGMA quick_check`（失敗したら**読み取り専用で起動**して復元を案内）／
   **日次は「写しを作り終えた後に、写しを開いて `quick_check` → `integrity_check`」**
   （**（P8-4 の監査 B-1）通らない写しは世代として採用しない**——一時フォルダを捨て、`last_error` に残し、
   `prune` を呼ばない。元の接続の `quick_check` も見て、走ったまま壊れていれば**読み取り専用に切り替える**）／
   復元後 `integrity_check`（**通らなければ元に戻す**）。
   **`-wal` / `-shm` を単独でコピーしない**（**必ず online backup API**）。
6. **版が上がるとき**: **上げる前に自動バックアップ**（取れなければ**上げない**）。
   **（E-2・P8-4 の監査）DB の版 > バイナリの版なら「起動を拒否」ではなく「読み取り専用で起動して案内」**
   （§10-13）。
   **（P8-4 の監査 D-2 / G-5）版を上げずに表の形を変えるとき（`_top_up_v6` の `ALTER`）も、
   変える前に控えを取る**（`pre-topup-<YYYYMMDD>-<HHMMSS>/`。`pre-migrate-*` と同じく**掃除の対象にしない**）。
   実データで `deletion_log.stuck_reason` が**控え無しで**足された（監査の事故 2 件目）ための規律。
   **足す物の一覧は `db.TOP_UP_COLUMNS` が正**（`_top_up_v6` と `missing_top_ups()` が同じ物を見る）。

### 0.15 「本文と食い違う点」の一覧（**§19 の点検が拾った物を含む**）

## 2. データモデル（v6）

### 2.1 DDL

```sql
-- ★ 段 1（論理削除）。**行は消さない**（判断と来歴を残す）。値の検査はサービス層（ALTER で CHECK を足せない）
ALTER TABLE asset ADD COLUMN deleted_at TEXT;   -- NULL = 生きている

-- 削除の台帳。**削除後も消さない**（専門 §3.2 の 4）
CREATE TABLE IF NOT EXISTS deletion_log (
  id           TEXT PRIMARY KEY,          -- ULID。**保留領域のフォルダ名にも使う**
  asset_id     TEXT,                      -- 内容（消しても残す）。**REFERENCES を張らない**
                                          --（asset を消す道を作らないため。内容が分からなくなっても id は残す）
  path         TEXT,                      -- 対象のパス（登録時の正規化した鍵）
  stage        INTEGER NOT NULL CHECK (stage IN (1, 2, 3)),
  from_path    TEXT,                      -- 段 2: 移動元
  to_path      TEXT,                      -- 段 2: 移動先（<data>/trash/…）
  hold_path    TEXT,                      -- 段 3: 保留領域（<data>/pending-delete/<id>/）。消したら「消えた」印にする
  remaining_sec INTEGER,                  -- 段 3: 取り消せる残り時間（秒。既定 300）。**単調時計で減らす**
  purge_at     TEXT,                      -- 段 3: 画面に出す**目安の壁時計時刻**。**NULL は「自動では消さない」**
  restored_at  TEXT,                      -- 段 3: 取り消した時刻（立てたら purge_at と remaining_sec を無効にする）
  size         INTEGER,                   -- 対象のバイト数（画面と frees に出す）
  request_id   TEXT REFERENCES delete_request(id),   -- ★（点検 A2）**再送の鍵は要求の単位**。行には持たせない
  reason       TEXT,
  -- ★（P8-3 の監査 G-3）**戻せなかった理由**（target_exists / move_failed / different / missing）。
  -- 段 3 の取り消しに失敗したときだけ入り、画面の「戻せませんでした」の 1 行を 4 通りに分ける。
  -- **版は上げずに足した**ので、古い v6 は `_top_up_v6` が `PRAGMA table_info` を見てから `ALTER`（家風）
  stuck_reason TEXT CHECK (stuck_reason IN ('target_exists', 'move_failed', 'different', 'missing')),
  actor        TEXT NOT NULL CHECK (actor IN ('human', 'agent')),
  at           TEXT NOT NULL
);
-- ★（点検 A2）**一括は 1 要求で最大 200 行**を書くので、`client_token` を行に持たせると 2 行目で UNIQUE に当たる。
-- 再送の鍵は**要求の単位**に置く。同じ token の再送は `result_json` をそのまま返す
CREATE TABLE IF NOT EXISTS delete_request (
  id           TEXT PRIMARY KEY,
  client_token TEXT,                      -- 再送の鍵（要求の単位）
  actor        TEXT NOT NULL CHECK (actor IN ('human', 'agent')),
  stage        INTEGER NOT NULL CHECK (stage IN (1, 2, 3)),
  count        INTEGER NOT NULL,
  result_json  TEXT,                      -- 実行の結果（同じ token の再送はこれを返す）
  at           TEXT NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_delete_token   -- **索引名は DB 全体で一意**（P6 の `review_request` の `ux_request_token` と衝突するので別名にする。`IF NOT EXISTS` は**黙って何もしない**＝穴が開く)
  ON delete_request(client_token) WHERE client_token IS NOT NULL;
CREATE INDEX IF NOT EXISTS ix_deletion_pending
  ON deletion_log(restored_at, purge_at) WHERE stage = 3;      -- 「最近の削除」を引く
CREATE INDEX IF NOT EXISTS ix_deletion_asset ON deletion_log(asset_id, at DESC);
CREATE INDEX IF NOT EXISTS ix_deletion_request ON deletion_log(request_id);

-- 「別物として確定」した組。**順序に依らず同じ行**（専門 §3.1 の点検 C10）
CREATE TABLE IF NOT EXISTS duplicate_exclusion (
  a_id   TEXT NOT NULL,
  b_id   TEXT NOT NULL,
  reason TEXT,
  actor  TEXT NOT NULL CHECK (actor IN ('human', 'agent')),
  at     TEXT NOT NULL,
  PRIMARY KEY (a_id, b_id),
  CHECK (a_id < b_id)                    -- ★ 正規化を機械的に守る（(A,B) と (B,A) を別行にしない）
);

-- 準重複の候補を絞る帯索引（**4bit × 16 本**。専門 §2.2。**（P8-1 の監査 B-1）8bit × 8 本から作り直した**）
CREATE TABLE IF NOT EXISTS phash_band (
  asset_id TEXT NOT NULL REFERENCES asset(id) ON DELETE CASCADE,
  band     INTEGER NOT NULL CHECK (band BETWEEN 0 AND 15),
  value    TEXT NOT NULL CHECK (length(value) = 1),   -- その帯の 4bit を 16 進 1 文字（小文字）
  PRIMARY KEY (asset_id, band)
);
CREATE INDEX IF NOT EXISTS ix_phash_band ON phash_band(band, value);

-- ★ 一括削除の凍結（専門 §3.5）。**DB に持つ**（再起動をまたいでも「確認した一覧」が失われない）
CREATE TABLE IF NOT EXISTS pending_delete_preview (
  id         TEXT PRIMARY KEY,           -- preview_id（ULID）
  stage      INTEGER NOT NULL CHECK (stage IN (1, 2, 3)),
  scope_json TEXT NOT NULL,              -- 何で選んだか（記録用。**実行時には評価しない**）
  items_json TEXT NOT NULL,              -- 凍結した一覧（asset_id / path / display_path / size / mtime_ns）。
                                         -- ★（点検 D6）**path は正規化した鍵・display_path は人に見せる元の表記**を両方持つ
                                         --   （画面に出すのは display_path。突き合わせは path）
  count      INTEGER NOT NULL,
  bytes      INTEGER NOT NULL,
  actor      TEXT NOT NULL CHECK (actor IN ('human', 'agent')),
  created_at TEXT NOT NULL,
  expires_at TEXT NOT NULL               -- 既定 10 分
);
CREATE INDEX IF NOT EXISTS ix_preview_expiry ON pending_delete_preview(expires_at);
```

- **`deletion_log.asset_id` に `REFERENCES` を張らない**（理由は DDL のコメント）。**`asset` の行は消さない**ので
  宙に浮くことはないが、**将来 `asset` を消す道を作ったときに台帳が消えない**ようにする。
- **`pending_delete_preview` は実行後に消す**（`DELETE`）。**失効した行は起動時と 1 時間ごとに掃除**（10 分を過ぎた物）。
- **`phash_band` は `asset` に `ON DELETE CASCADE`**（内容が消えれば帯も要らない）。
- **`duplicate_exclusion` は `asset` を参照しない**（内容の id を持つだけ。**除外は人が戻すまで残す**）。

### 2.2 表を足すときの約束（P7 の教訓）

- **`CHECK` は `ALTER` で足せない。** 新表は**最初から付ける**。**既存の表に足す値**（`asset.deleted_at` は列、
  `review_group.kind` に `duplicate` を許すか）は**サービス層で検査**し、**表の作り直しはしない**
  （実データに 263 枚と判断 3 件が入っている。**空の表なら作り直すが、この段では空ではない**）。
- **`seed` NULL と UNIQUE の型の罠**（P7-A-2c）: **NULL を含む一意性**が要る所は
  **`COALESCE(…)` の式の索引**か**部分索引**にする。この段では **`ux_delete_token   -- **索引名は DB 全体で一意**（P6 の `review_request` の `ux_request_token` と衝突するので別名にする。`IF NOT EXISTS` は**黙って何もしない**＝穴が開く)`（要求の単位。部分索引）**と
  **`ux_recipe_source` 相当の物**（**（点検 A2）行ごとの `ux_deletion_token` は一括で 2 行目に当たるのでやめた**）。
- **移行は足すだけ・何度呼んでも同じ**（`migrate()` は `current < 6` を 1 回だけ当てる）。
