## 0. 拘束力のある差分（本文と食い違う点・本文が黙っている点）

### 0.1 段の分け方と合格の線

利用者の優先は **① 重複の検出と整理 → ② 削除と取り消し**（§0.2）。**バックアップは 3 番目**。
だから段をこう割る（**P8-4 までを「合格の線」に数え、P8-5 は数えない**。P5 の P5-3 と同じ扱い）:

| 小段 | 何を作るか | 合格の線 | 監査の単位 |
| --- | --- | --- | --- |
| **P8-0** | **機能を足さない。** v6 の表（`deletion_log` / `duplicate_exclusion` / `phash_band` / `pending_delete_preview`）と `asset.deleted_at`、契約、`backup-manifest` の形 | §1.2 の線 1（表が正しい・移行が何度でも安全） | 表と契約（P4-0・P6-0・P7-0 と同じ観点） |
| **P8-1** | **重複の検出と整理**（pHash の全件計算・`phash_band`・完全重複と準重複の一覧・「別物として確定」と解除・まとまりの作成） | **線 2・3・4**（実データで 21 群が出る・代表を選べる・除外が効く） | 検出の正しさと**誤検出の扱い** |
| **P8-2** | **削除の 3 段階と 5 分の取り消し**（論理削除・ゴミ箱・保留領域・`最近の削除`・一括削除の凍結と実行） | **線 5・6・7・8**（消せる・戻せる・上書きしない・一括が凍結どおり） | **取り返しのつかなさ**（保留領域・取り消し・安全規則） |
| **P8-3** | **参照切れと再リンク**（`missing_at` の既存の道・近くを探す・場所を指定・走査での自動つなぎ） | 線 9 | 再リンクが**中身を確かめてから**繋ぐか |
| **P8-4** | **バックアップと復元**（日次スナップショット・`backup` / `restore` / `rebuild-metadata`・健全性） | 線 10・11・12 | **`<data>` を消しても戻せるか**（実際に消して試す） |

**理由**: 利用者の 2 つの困りごとは P8-1 と P8-2 で消える。**ここまでを先に「合格」にする**。
画面が無くても口（API）で価値が出る（重複の一覧と削除は口で使える）。P8-5 は**その上に載せる**。

### 0.4 **完全重複はこの実データでは空振り。本体は準重複**（**実測**）

| 種類 | 定義 | **実データ（263 枚）** |
| --- | --- | --- |
| 完全重複 | 同じ `sha256` が 2 か所以上（`asset_location` が 2 行以上） | **0 群**（263 枚すべて 1 か所） |
| **準重複** | pHash のハミング距離 **≤ 6** | **21 群 / 57 枚**（2 枚が 10 群・3 枚が 7 群・4 枚が 4 群） |
| ほぼ同じ絵 | 距離 **≤ 3** | 17 群 / 39 枚（**距離 0 が 9 組**） |
| 同じ生成条件 | `meta` の `seed` が同じ | 19 群（**最大 31 枚**。**要確認**＝バッチ生成の可能性。§10） |

- **完全重複の検出は実装するが、この環境では 0 件**。画面は**空のときに「完全重複はありません」と 1 行出す**
  （**空の一覧を黙って出すと「壊れている」と思われる**）。
- **準重複が本体**。実例（§1.3）: 1024×1024 が 4 枚（サイズが 1179/1183/1138/1166 KB）＝**同じ絵の別ファイル**、
  1024/1536/2048 の 3 枚＝**リサイズ違い**。**専門文書 §2.2 の 2 種類が実データにある。**
- **`asset.sha256` の `UNIQUE` があるので「同じ中身の 2 行」は構造的に作れない**（専門 §2.1）。
  つまり**完全重複は「同じ絵を 2 か所に置いた」ときだけ**出る。**この使い方は今の利用者には無い**（1 か所しか置いていない）。

### 0.5 pHash は**全件計算が要る**（実測: 14.8 ms/枚）

- 実データで **pHash が入っているのは 91 / 263 枚**（P5-3 はサムネイルを作る復号に同居して入れる＝
  **見た画像から入る**）。**未計算の 172 枚を計算するのに 2.6 秒**（14.8 ms/枚・**復号込み**。私の実測）。
  → **1 万枚なら約 2.5 分**（`comparison.md` §7 の「8 ms/枚・2 分以内」は**復号を含まない見積り**だった。
  **この段で実測に置き換える**）。
- **だから `GET` では計算しない**（家風: `GET` は 1 バイトも書かない。§0.13）。
  **`POST /api/duplicates/compute`（背景ジョブ）で足りない分を計算**し、`GET /api/duplicates/near` は
  **計算済みの物だけ**から候補を返す。**未計算の枚数**を応答に出す（例: `"unhashed": 172`）。
- **`phash_band` は `asset.phash` が入ったときに一緒に書く**（`compare.capture_hashes` / `ensure_hashes` の
  隣に 1 手足す）。**帯の値は 16 進 2 文字**（専門 §1.3）。

### 0.6 削除の 3 段階と 5 分の窓（**「アプリが動いていた時間」で数える**）

専門文書 §3.1・§3.4 のとおり。**この段で特に守る 4 点**:

1. **段 3 は即座に unlink しない。** **同じボリューム**の `<data>/pending-delete/<削除ID>/` へ `os.replace` で移す
   （**名前の付け替えなので一瞬**）。
2. **窓は `remaining_sec` を単調時計で減らして数える**（**壁時計では数えない**）。30 秒ごとに前回からの経過を引く。
   **スリープ・休止・終了の間は進まない**。**`purge_at` は画面に出す目安の壁時計時刻**で、
   **自動削除の判定には使わない**（専門 §3.4 の点検の誤りをそのまま守る）。
3. **起動時には絶対に消さない。** 残り時間を引き継いで「最近の削除」に戻し、タイマーを張り直す。
   **`purge_at IS NULL` の行（戻せなかった物）はタイマーの対象にしない**。
4. **取り消しは元のパスを上書きしない。** 埋まっていたら**別名で戻す**か尋ねる。**失敗したら `purge_at` を `NULL` にして
   自動削除から外す**（黙って再試行しない）。
5. **（Q2 の帰結 c・d）エージェントの削除も同じ窓で数える。** 誰が消したかで**窓の長さを変えない**（人もエージェントも 5 分）。
   **`deletion_log.actor` に `human` / `agent` を必ず入れる**。**1 回の要求で消す枚数の上限は 200**
   （超えたら **422 `too_many`** で**1 枚も消さない**。一括の `preview` も同じ上限）。

- **別ボリュームのときの保留領域**（専門 §7-6 の未確認）: **既定は `<data>/pending-delete/`**。
  **同じボリュームでない場合は「段 3 を断る」**（`409 cross_volume`）ことを**この段の決定**とする。
  理由: 別ボリュームへ移すと**コピーになり、大きいファイルで待たされ、途中で失敗すると中途半端**になる
  （専門 §3.4 が禁じている）。**安全側に倒して「いまはできない」と言う**方が、壊れるより良い。
  **画面には理由と対処（エクスプローラで消す）を出す。**

### 0.7 一括削除は**凍結 → 実行**（10 分で失効）

専門文書 §3.5 のとおり。**この段の決定**:

- 凍結は **DB の `pending_delete_preview`** に持つ（§0.3）。
- **実行の直前に 1 件ずつ `(size, mtime_ns)` を再照合**し、食い違った項目は **`skipped` にして残りは消す**。
- **`preview_id` は既定 10 分で失効**。失効したら**何も消さず `409 preview_expired`**。
- **`frees`（何がいつ空くか）**: 段 1 は 0（カタログから外すだけ）／段 2 はゴミ箱の掃除まで空かない／
  段 3 は**5 分の窓が過ぎた時点**。**画面にこの 3 つを出す**（「消したのに空きが増えない」と思わせない）。

### 0.8 重複の整理は**既存のまとまりレビューを使う**（専用の画面を作らない）

専門文書 §2.2 の決定。**`review_group` に `kind='duplicate'` / `policy='pick_one'` のまとまりを作り**、
**既存の「まとまりレビュー」の画面で 1 枚選ぶ / 全部ボツ / 保留**ができる（P5-1 で作ってある）。
**重複専用の概念を増やさない。**

- 実データの `review_group` は 1 件・`kind` の語彙に `duplicate` があるか**要確認**（§10）。
  無ければ **`CHECK` を張り直すのではなく**、`kind` の値を**サービス層で検査**する（`ALTER` で `CHECK` は足せない）。
- まとまりの作成は**人が押したときだけ**（**自動でまとめない**。専門 §2.4）。

### 0.9 代表の選び方（**設計者が決めた**）

専門文書は「代表を 1 つ選んで他を外す」と言うが、**どれを代表にするかの規則を書いていない**。決める:

| 優先 | 規則 | 理由 |
| --- | --- | --- |
| 1 | **人が選んだ物**（`decision` が `keep`） | 人の判断が最優先 |
| 2 | **画素数が最大**の物 | リサイズ違いなら**元の解像度**を残す |
| 3 | **ファイルが大きい**物 | 画素数が同じなら情報量が多い |
| 4 | **`first_seen_at` が古い**物 | 先に入った物（作り直しの元）を残す |
| 5 | `id` の昇順 | **決定的にする**（同じ入力なら同じ答え） |

- **画面には「おすすめ」として出すだけ**。**自動では外さない**（専門 §2.4）。
- **`GET /api/duplicates/near` の各群に `suggested_id` を入れる**（規則を 1 か所に持つ）。

### 0.10 誤検出と除外（**解除できること**）

専門文書 §2.4・§3.1 のとおり。**`duplicate_exclusion` は `(小さい方, 大きい方)` に正規化**し、
**`CHECK (a_id < b_id)`** で機械的に守る。**`DELETE /api/duplicates/exclude` を必ず用意**（解除）。

- **除外した組は候補に出さない**が、**`deletion_log` には書かない**（除外の解除で行が消えるので、
  「いつ誰が除外したか」は `duplicate_exclusion` の行そのものが持つ。専門 §3.1 の注記）。

### 0.11 再リンク（**中身を確かめてから繋ぐ**）

専門文書 §4 のとおり。**新しい仕組みは作らない**（`asset_location.missing_at` と `location_history` は既にある）。

- 手段は 3 つ: **近くを探す**（同じルート内をファイル名で探し、**ハッシュが一致すれば繋ぐ**）／
  **場所を指定**（ファイル選択。**ハッシュを確かめてから**）／**自動**（走査のたびに一致する新規ファイルを繋ぐ）。
- **中身が違えば繋がない**（`sha256` の一致を必須にする）。**`size` と `mtime_ns` は見ない**
  （移動で mtime は変わりうる。**中身のハッシュが正**）。
- `location_history` に「入れ替わった」「繋ぎ直した」を残す（**既存の表を使う**）。

### 0.12 バックアップ（**`<data>` の外に置く**）

専門文書 §5 のとおり。**この段の決定**:

1. **日次スナップショットは起動時に 1 日 1 回**（同じ日に既に取っていれば何もしない）。
   `sqlite3.Connection.backup()` で DB を取り、**`sidecar/` と `export/` も同じスナップショットに入れる**
   （**`sidecar/` は PNG から取り直せない唯一のもの**。実データに **1 ファイル**あった）。
   **画像とサムネイルは入れない**（参照モードでは画像は利用者の資産。`thumbs` は 297 ファイルあるが再生成できる）。
2. **置き場の既定は `<data>` の外**: `%USERPROFILE%\image-reviewer-backups\<YYYYMMDD>\`
   （設定 `backup_dir`・環境変数 `IMAGE_REVIEWER_BACKUP_DIR`）。
   **理由**: `<data>` を消したときに備える対策を `<data>` の中に置くと**論理が閉じない**（専門 §5.1 の注記）。
3. **直近 7 個を残す**。`manifest.json` に**版・件数・作った時刻・含めた範囲**を書く。
4. **CLI**: `image-reviewer backup --out <dir> [--include-library]` / `image-reviewer restore <dir> [--force]` /
   **`image-reviewer rebuild-metadata`**（PNG と sidecar から来歴を組み直す。**既存の `capture.py` の
   `write_sidecar` の形を使う**）。**`rebuild-metadata` は P8 で作る**（専門 §5.2 の 4 の約束）。
5. **健全性**: 起動時 `PRAGMA quick_check`（失敗したら**読み取り専用で起動**して復元を案内）／
   日次で `integrity_check`／復元後 `integrity_check`（**通らなければ元に戻す**）。
   **`-wal` / `-shm` を単独でコピーしない**（**必ず online backup API**）。
6. **版が上がるとき**: **上げる前に自動バックアップ**。**DB の版 > バイナリの版なら起動を拒否**（前方のみ）。

### 0.13 規律（前の段で踏んだ穴を最初から塞ぐ）

| 規律 | この段での具体 |
| --- | --- |
| **`GET` は 1 バイトも書かない** | `GET /api/duplicates/*` は**計算しない**（§0.5）。`GET /api/pending-deletes` も**残り時間を減らさない**（減らすのはタイマー） |
| **`actor` の検査は 1 か所** | **削除（段 1〜3・一括・その取り消しの一覧）は人もエージェントも可**（**利用者の回答 Q2。推奨の「人だけ」とは違う**）。**除外・復元・バックアップは `human` だけ**（`require_human`。`403 human_only`）。**`require_human` を 1 か所に集め、削除の 3 口だけ開ける**（**後で「人だけ」に戻すのは 1 行**） |
| **`actor` を必ず残す** | 削除の台帳（`deletion_log.actor`）と**画面の「誰が」**（**Q2 の帰結 a・b**）。**語彙外は 422**（`CHECK` に当てて 500 にしない） |
| **消す量に上限** | **1 回の要求で 200 枚まで**（**Q2 の帰結 d**）。超えたら **422 `too_many`** で**1 枚も消さない**（**部分適用しない**） |
| **`client_token`** | **段 2・段 3 の実行**と**一括削除の実行**に付ける（**再送で二重に消さない**）。同じ token の再送は**200 で前の結果**を返す |
| **取引の外で外部を待つ** | ファイル操作（`os.replace`・`unlink`）は**取引の外**。取引は**台帳の 1 行**だけ |
| **原子性** | sidecar・スナップショット・`manifest.json` は**一時ファイル → `os.replace`** |

## 2. データモデル（v6）

### 2.1 DDL

```sql
-- ★ 段 1（論理削除）。**行は消さない**（判断と来歴を残す）。値の検査はサービス層（ALTER で CHECK を足せない）
ALTER TABLE asset ADD COLUMN deleted_at TEXT;   -- NULL = 生きている

-- 削除の台帳。**削除後も消さない**（専門 §3.2 の 4）
CREATE TABLE IF NOT EXISTS deletion_log (
  id           TEXT PRIMARY KEY,          -- ULID。**保留領域のフォルダ名にも使う**
  asset_id     TEXT,                      -- 内容（消しても残す）。**REFERENCES を張らない**
                                          --（asset を消す道を作らないため。内容が分からなくなっても id は残す）
  path         TEXT,                      -- 対象のパス（登録時の正規化した鍵）
  stage        INTEGER NOT NULL CHECK (stage IN (1, 2, 3)),
  from_path    TEXT,                      -- 段 2: 移動元
  to_path      TEXT,                      -- 段 2: 移動先（<data>/trash/…）
  hold_path    TEXT,                      -- 段 3: 保留領域（<data>/pending-delete/<id>/）。消したら「消えた」印にする
  remaining_sec INTEGER,                  -- 段 3: 取り消せる残り時間（秒。既定 300）。**単調時計で減らす**
  purge_at     TEXT,                      -- 段 3: 画面に出す**目安の壁時計時刻**。**NULL は「自動では消さない」**
  restored_at  TEXT,                      -- 段 3: 取り消した時刻（立てたら purge_at と remaining_sec を無効にする）
  size         INTEGER,                   -- 対象のバイト数（画面と frees に出す）
  client_token TEXT,                      -- 再送の鍵（段 2・段 3）
  reason       TEXT,
  actor        TEXT NOT NULL CHECK (actor IN ('human', 'agent')),
  at           TEXT NOT NULL
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_deletion_token
  ON deletion_log(client_token) WHERE client_token IS NOT NULL;
CREATE INDEX IF NOT EXISTS ix_deletion_pending
  ON deletion_log(restored_at, purge_at) WHERE stage = 3;      -- 「最近の削除」を引く
CREATE INDEX IF NOT EXISTS ix_deletion_asset ON deletion_log(asset_id, at DESC);

-- 「別物として確定」した組。**順序に依らず同じ行**（専門 §3.1 の点検 C10）
CREATE TABLE IF NOT EXISTS duplicate_exclusion (
  a_id   TEXT NOT NULL,
  b_id   TEXT NOT NULL,
  reason TEXT,
  actor  TEXT NOT NULL CHECK (actor IN ('human', 'agent')),
  at     TEXT NOT NULL,
  PRIMARY KEY (a_id, b_id),
  CHECK (a_id < b_id)                    -- ★ 正規化を機械的に守る（(A,B) と (B,A) を別行にしない）
);

-- 準重複の候補を絞る帯索引（8bit × 8 本。専門 §2.2）
CREATE TABLE IF NOT EXISTS phash_band (
  asset_id TEXT NOT NULL REFERENCES asset(id) ON DELETE CASCADE,
  band     INTEGER NOT NULL CHECK (band BETWEEN 0 AND 7),
  value    TEXT NOT NULL,               -- その帯の 8bit を 16 進 2 文字（小文字）
  PRIMARY KEY (asset_id, band)
);
CREATE INDEX IF NOT EXISTS ix_phash_band ON phash_band(band, value);

-- ★ 一括削除の凍結（専門 §3.5）。**DB に持つ**（再起動をまたいでも「確認した一覧」が失われない）
CREATE TABLE IF NOT EXISTS pending_delete_preview (
  id         TEXT PRIMARY KEY,           -- preview_id（ULID）
  stage      INTEGER NOT NULL CHECK (stage IN (1, 2, 3)),
  scope_json TEXT NOT NULL,              -- 何で選んだか（記録用。**実行時には評価しない**）
  items_json TEXT NOT NULL,              -- 凍結した一覧（asset_id / path / size / mtime_ns）
  count      INTEGER NOT NULL,
  bytes      INTEGER NOT NULL,
  actor      TEXT NOT NULL CHECK (actor IN ('human', 'agent')),
  created_at TEXT NOT NULL,
  expires_at TEXT NOT NULL               -- 既定 10 分
);
CREATE INDEX IF NOT EXISTS ix_preview_expiry ON pending_delete_preview(expires_at);
```

- **`deletion_log.asset_id` に `REFERENCES` を張らない**（理由は DDL のコメント）。**`asset` の行は消さない**ので
  宙に浮くことはないが、**将来 `asset` を消す道を作ったときに台帳が消えない**ようにする。
- **`pending_delete_preview` は実行後に消す**（`DELETE`）。**失効した行は起動時と 1 時間ごとに掃除**（10 分を過ぎた物）。
- **`phash_band` は `asset` に `ON DELETE CASCADE`**（内容が消えれば帯も要らない）。
- **`duplicate_exclusion` は `asset` を参照しない**（内容の id を持つだけ。**除外は人が戻すまで残す**）。

### 2.2 表を足すときの約束（P7 の教訓）

- **`CHECK` は `ALTER` で足せない。** 新表は**最初から付ける**。**既存の表に足す値**（`asset.deleted_at` は列、
  `review_group.kind` に `duplicate` を許すか）は**サービス層で検査**し、**表の作り直しはしない**
  （実データに 263 枚と判断 3 件が入っている。**空の表なら作り直すが、この段では空ではない**）。
- **`seed` NULL と UNIQUE の型の罠**（P7-A-2c）: **NULL を含む一意性**が要る所は
  **`COALESCE(…)` の式の索引**か**部分索引**にする。この段では `ux_deletion_token` が**部分索引**。
- **移行は足すだけ・何度呼んでも同じ**（`migrate()` は `current < 6` を 1 回だけ当てる）。

| `GET /api/duplicates/exact` | 人・エージェント | 完全重複（2 か所以上の `asset`）の一覧 | **この環境では 0 群**。`count: 0` と `message` を返す |
| `POST /api/duplicates/compute` | **人だけ** | 足りない pHash を計算する**背景ジョブ**（`job` を使う） | **202** で job を返す。`force` で全件やり直し |
| `GET /api/duplicates/near` | 人・エージェント | 準重複の群（`max_distance` 既定 6・`limit`・`cursor`） | **計算しない**。`unhashed`（未計算の枚数）を返す。各群に `suggested_id`（§0.9） |
| `POST /api/duplicates/exclude` | **人だけ** | 「別物として確定」 | `(min, max)` に正規化。`reason` |
| `DELETE /api/duplicates/exclude` | **人だけ** | **解除**（必須。専門 §3.1 の点検 C10） | 本文は `POST /api/duplicates/exclude/remove` にする（**`DELETE` に本文を持たせない**。§0.15 の 1） |
| `POST /api/groups` | **人だけ** | 群から**まとまりを作る**（`kind='duplicate'`, `policy='pick_one'`） | **既存の口を使う**（新設しない）。1 群 1 まとまり |

### 3.2 削除（P8-2）

| 口 | 誰 | 何 | 備考 |
| --- | --- | --- | --- |
| `POST /api/locations/delete` | **人・エージェント** | 1 件を段 1〜3 で消す | `{asset_id, path, stage, reason?, client_token?}`。**`DELETE` ではなく `POST`**（§0.15 の 1）。**`deletion_log.actor` に誰が消したかを残す**（Q2 の帰結 a） |
| `POST /api/locations/bulk-delete/preview` | **人・エージェント** | 対象を**凍結**する | `{scope, stage}` → `{preview_id, items, count, bytes, frees, expires_at}`。**200 枚を超えたら 422 `too_many`**（Q2 の帰結 d） |
| `POST /api/locations/bulk-delete` | **人・エージェント** | 凍結した一覧を実行 | `{preview_id, confirm:true, client_token?}` → `{deleted, skipped, count, bytes}`。**上限 200**（凍結の時点で弾く） |
| `GET /api/pending-deletes` | 人・エージェント | **取り消せる削除**の一覧（残り時間つき。**誰が消したか**も返す） | **残り時間を減らさない**（減らすのはタイマー） |
| `POST /api/pending-deletes/{id}/undo` | **人だけ** | 取り消す（上書きしない。埋まっていれば `?as_copy=1` で別名） | `409 target_exists` のときは別名の確認。**エージェントは一覧を見て人に知らせる**（§0.14 の決定。**§12 で迷いとして残す**） |
| `GET /api/trash` | 人・エージェント | ゴミ箱の一覧（日付ごと） | **メインの一覧とは別**（§0.15 の 5） |
| `POST /api/trash/restore` | **人だけ** | ゴミ箱から戻す | `{deletion_id}` |
| `POST /api/locations/relink` | **人だけ** | 参照切れを繋ぐ | `{asset_id, path, mode:'nearby'|'exact'}`。**`sha256` が一致しなければ 409** |

### 3.3 バックアップ（P8-4）

| 口 | 誰 | 何 |
| --- | --- | --- |
| `POST /api/backup` | **人だけ** | いま 1 回取る（`{include_library:false, out?}`）。**同じ日なら 200 で既存を返す**（`client_token` は付けない。日付が鍵） |
| `GET /api/backup` | 人・エージェント | 直近のスナップショットの一覧と**最後に取った時刻**・置き場・次に取る予定 |
| `POST /api/backup/restore` | **人だけ** | 復元（`{path, force:false}`）。**先に自動バックアップを取る** |
| `GET /api/health/db` | 人・エージェント | `quick_check` / `integrity_check` の結果と**読み取り専用かどうか** |

### 3.4 エラーの形（前の段と同じ）

| 状況 | 番号 | `code` |
| --- | --- | --- |
| 対象が登録された場所に無い（削除・再リンク） | **409** | `not_registered` |
| `size` / `mtime_ns` が登録と違う | **409** | `changed` |
| 保留領域が対象と別ボリューム（別ドライブ） | **409** | `cross_volume` |
| 元の場所が埋まっている（取り消し） | **409** | `target_exists` |
| `preview_id` が失効 | **409** | `preview_expired` |
| 実行中に走査ジョブがある | **409** | `scan_running` |
| 中身が違う（再リンク） | **409** | `hash_mismatch` |
| **1 回の要求が上限（200 枚）を超えた**（削除・一括の凍結） | **422** | `too_many`（**1 枚も消さない**。Q2 の帰結 d） |
| エージェントが**除外・復元・バックアップ**を呼んだ（**削除は許す**。Q2） | **403** | `human_only` |
| `stage` の語彙外・`actor` の語彙外 | **422** | `bad_stage` / `bad_actor` |
| DB が壊れていて書き込みを止めている | **503** | `read_only` |

## 6. 契約

### 6.1 `review.json` は**変えない**（この段の決定）

- **段 1 で外した資産も、判断つきで出し続ける。** 台帳は画像より長く生きる（専門 §3.2 の 4）。
  実体が無いことは**既存の `missing`**（`design.md` §6.2 の `Asset`）で表せるので、**欄を足す必要が無い**。
- **`review-export.schema.json` を触らない。** **テストで「足していない」ことを固定する**
  （P7-0 と同じ形。`tests/test_export.py` に 1 件足す）。
- **理由**: 利用者は他のツールと連携していない（`design.md` §18）。契約を増やす価値より、
  **下流（自分の将来の道具）が壊れない**方が大事。

### 6.2 新しく足す契約は 2 つ

| 契約 | 何 | 誰が読むか |
| --- | --- | --- |
| **`schemas/backup-manifest.schema.json`** | 日次スナップショットの `manifest.json`（版・作った時刻・件数・含めた範囲・DB の `sha256`） | `restore` が**自分で読む**（復元前に版と件数を出す） |
| **`schemas/deletion-ledger.schema.json`** | **削除の台帳**（`<data>/export/deletions.json`）。人が読める形 | 利用者（「なぜ消したか」を後から見る）。**P8-4 で書き出す** |

- `manifest.json` の中身（案）:
  ```json
  {"schema": "urn:image-reviewer:backup-manifest", "abi": "0.1", "app_version": "0.0.1",
   "created_at": "2026-10-17T03:00:00Z", "data_dir": "C:\\work\\image-reviwer\\.data",
   "includes": {"db": true, "sidecar": true, "export": true, "library": false},
   "counts": {"assets": 263, "decisions": 3, "groups": 1, "annotations": 0, "tags": 0},
   "db_sha256": "sha256:…", "db_bytes": 1003520}
  ```
- **`sidecar` の形は変えない**（専門 §5.6。`capture.py` の `write_sidecar` が既にこの形）。
  **`abi` は `0.1` のまま**（足すだけなので上げない。P6 の規則）。

### 6.3 `review.json` と削除の関係（**規則を 1 つに決める**）

| 状態 | `review.json` に |
| --- | --- |
| 生きている | 出る（今と同じ） |

## 7. 性能

**測った物と未計測を分ける**（P4 の教訓）。

| 操作 | 目標 | 根拠 |
| --- | --- | --- |
| **pHash の全件計算（263 枚・未計算 172 枚）** | — | **実測 2.6 秒・14.8 ms/枚（復号込み）**（§1.3。**私の実測**） |
| pHash の全件計算（1 万枚） | 3 分以内 | 実測 14.8 ms/枚からの換算（**約 2.5 分**）。**`comparison.md` §7 の「8 ms/枚」は復号を含まない見積り。この段で実測に置き換えた** |
| 完全重複の検出 | 100 ms 以内 | `GROUP BY` 1 本（専門 §6）。**263 枚では 1 ms 未満（未計測。P8-1 で測る）** |
| 準重複の検出（263 枚） | — | **未計測**（帯索引を作った後の候補数による。P8-1 で測る） |
| 準重複の検出（1 万枚） | 2 秒以内 | 帯索引で候補を絞る（専門 §6）。**未計測** |
| 段 3 の移動（`os.replace`） | ファイルサイズに依存しない | 同一ボリュームの名前の付け替え（専門 §3.4）。**未計測**（P8-2 で 1 GB 級を作って測る） |
| 一括削除の再照合 | 1,000 件で 1 秒以内 | `os.stat` 1 回/件。**未計測** |
| 日次バックアップ | 5 秒以内 | DB 1.0 MB ＋ `sidecar` 1 ファイル ＋ `export` 1 ファイル（実データ）。**未計測**（P8-4 で測る） |
| 復元 | 10 秒以内 | DB のコピーと `quick_check`。**未計測** |

- **計測は別々の入力で、測り方（何回の中央値か）を書く**（P4・P6 の教訓）。
  **`execution_cached` のような「キャッシュに当たった値」を実測と呼ばない**（P4 の教訓）。

## 11. 用語

| 語 | 意味 |
| --- | --- |
| **段 1 / 2 / 3** | 削除の 3 段階（カタログから外す / ゴミ箱へ移す / 実ファイルを消す） |
| **保留領域** | `<data>/pending-delete/<削除ID>/`。**5 分の窓のためだけ**に使う（同じボリューム） |
| **窓** | **削除後 5 分**。**アプリが動いていた時間**で数える（スリープ・終了の間は進まない） |
| **凍結（preview）** | 一括削除の対象を**1 回だけ解決して保存**した物。**実行時に評価し直さない** |
| **`frees`** | その段で**いつ容量が空くか**（段 1 は空かない・段 2 は掃除まで・段 3 は窓の後） |
| **帯（`phash_band`）** | 64bit の pHash を 8bit × 8 本に割った物。**距離 ≤ 6 なら必ず 1 本は一致する** |
| **代表** | 重複の群で残す 1 枚。**推薦するだけ**（自動では外さない） |
| **除外** | 「別物として確定」した組（`duplicate_exclusion`）。**解除できる** |
| **取り返しのつかなさの順** | 段 1 → 段 2 → 段 3（この順に危ない） |
