## 3. 何を確かめるか

1. **各報告の §H（確かめられなかったこと＋依頼者が打てる確認手順）を、実際に打って判定する。**
   3 報告すべてに §H があります。**あそこに書かれた手順は、あなた自身が書いたものです。**
2. **各報告の A / B / C のうち「実行していない」と付いた項目を、実行で再現確認する。**
   1 件ずつ「再現した / しなかった / 実行で別の原因が分かった」を書く。
3. **監査後に直したとされる箇所**（`README.md` と `p5-design.md` が 2026-10-15 20:15 に「反映済み」としている）が、
   **実際に直っているか**を実行で確かめる。とくに P5-3 の次の 3 件:
   - **A1**: `hidden` 属性が作者の `display: flex` に打ち消されないか（比較画面のヒートマップ帯とタイル）。
   - **A2**: 位置合わせの「別の絵の可能性が高い」判定（`peak_ratio` の閾値）が実際に発火するか。
   - **A3**: 比較文書がサムネイルより先に作られ、既存 263 枚で「似ている順」が出ない問題。
   **コードを読んだだけの判断は「読んだだけ」と明記**してください。
4. **実行して初めて分かること**を、「最も重大な 3 件」に最低 1 件入れる（前回はこれが満たせませんでした）。
5. 設計の点検（`review-report.md` / `p5-review-report.md` / `review-triage-fable.md`）が
   **「実行して確かめてよい条件」で残した項目**（例: `tabular-nums` が BIZ UDPGothic で効くか、
   `control_after_generate` の復元、`POST /api/userdata` の実書き込み、保留領域の別ボリューム）は、
   **この環境で実行できるものだけ**確かめ、**できないもの（ComfyUI の実生成が要る等）は「できない理由」を書く**。

## 4. 報告の形式（各ファイル）

```markdown
# P5 実装の監査報告（実行込みのやり直し）

- 監査した版: 2026-10-15 の作業ツリー（git 管理外。更新時刻は実行して取る）
- **実行できたかどうか**: 実行したコマンドと結果の要約。実行していないものは「実行していない」と明記
- 総合判定: 使える / 条件つきで使える / 作り直す

## A. 設計の主張が成り立たない（必ず直す）
## B. 重大（静かに間違える・遅い）
## C. 中程度
## D. 軽微
## E. 設計・ドキュメントとのずれ
## F. テストが守っていないもの
## G. 依頼者への質問
## H. 今回も確かめられなかったこと（＋できない理由）
## R. 前回の指摘の再判定（前回の A/B/C/§H の各項目 → 再現した / しなかった / 判定不能＋根拠）
```

- 各項目に**必ず「場所」**（ファイルと行）と、**実行したコマンド or 再現手順**。
- **前回と同じ指摘は §R に集約**し、**A〜D は実行で新たに分かったこと**を優先して書く。
- **問題が無いと確認した観点は 1 行**で「確かめた結果、問題なし」。
- 最後に**最も重大な 3 件**を理由 2〜3 文で。うち 1 件以上は**実装者が気づいていないもの**。
