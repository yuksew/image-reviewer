## 1. 守ること

1. **`docs/review-report.md` 以外のファイルを変更しない。** 設計文書を直したくなっても、それは書きません。
   直し方は「提案」として報告に書いてください（直すのは依頼者の仕事です）。
2. **コードを書かない。** この段階では設計の妥当性だけを見ます。
3. **称賛は要りません。** 見つけた問題と、その根拠だけを書いてください。
   良い点を書くなら、その後に「では何が足りないか」を続けてください。
4. **推測で断定しない。** 文書に書かれていないことは「書かれていない」と指摘してください。
   事実（実測値など）と設計判断を区別してください。

## 2. この道具は何か

画像を溜めて、見て、**キープ / ボツ**を決めるためのローカルツールです。

| 項目 | 内容 |
| --- | --- |
| 使う人 | 1 人（イラストの生成と選別を自分で行う） |
| 目的 | 大量の候補から**気に入ったものを残す**。エージェントの求めに応じて判断を返す |
| 形態 | `127.0.0.1:8790` の Web アプリ。ショートカットで起動し、タスクトレイに常駐 |
| 想定規模 | 数千枚（〜1 万枚） |
| 技術 | Python 3.12 / uv / FastAPI / SQLite(WAL) / Pillow / onnxruntime-gpu。前面は素の TypeScript + Vite |
| 接続先 | **ComfyUI だけ**（他のツールとは連携しない） |

**画像は ComfyUI で生成したものが中心**です。その PNG には生成条件（`prompt` チャンク）が埋まっていますが、
**日本語→英語の翻訳結果は埋まっていません**（実行時の値で、`/history` にもメモリ上しか残らない）。
これが設計の多くの判断の出発点になっています。

## 3. 利用者が確定した決定（これを覆す提案は「矛盾」として扱う）

設計文書がこの一覧と食い違っていたら、**それを指摘してください**。これがあなたの最も価値の高い仕事です。

**作るもの**
- 独立した新ツール。**他のツールとは完全に切り離す**（コード・データ・語彙・規約のいずれも合わせない。将来も連携しない）
- ローカル Web アプリ。ショートカット起動、タスクトレイ常駐
- 前面は素の TypeScript + Vite（React 等は使わない）
- 名前は `image-reviewer`。データ置き場は `<リポジトリ>/.data`
- 進め方: 設計書 → 点検（あなた） → 実装 → 監査（あなた）

**画像**
- 対象: 自分の生成物（Anima 他）／**参考資料（他人の絵）**／**写真・スクリーンショット**
- 形式: **PNG と JPEG**
- 種別（生成物 / 参考資料 / 写真）は自動判定し、**人が直せる**
- 参考資料には出所 URL・種別・「何の参考か」の自由記述を持たせる（**省略可**）
- 取り込み: フォルダ走査 / ドラッグ&ドロップ / クリップボード / **画像 URL を貼る**
  （クリップボードの中身が URL で拡張子が画像なら取り込みを試みる）
- 「保存」に含めるのは登録と取り込みまで。**書き出し・改名・メタデータの埋め込みは対象外**
- 参照を既定、取込（コピー）も選べる

**見る・探す**
- カタログは仮想の入れ物（**1 枚が複数所属可**）＋ スマートフォルダ
- 画面は日本語、Danbooru タグは英語 ＋ **日本語の語釈を 2 行目**（**括弧書きは使わない**）
- タグは**詳細と拡大だけ**に出す。語釈の訳は **ComfyUI の `TextGenerate`**、**見えた語だけ遅延**、保存して**人が直せる**
- グリッドの見た目（密度・テーマ）は**切替できる**ようにする
- タグの編集機能（語の統合・改名）は**作らない**

**判断**
- 言葉は **キープ / ボツ**（契約値は `kept` / `rejected`、`keep` / `reject` / `clear`）
- 「採用」＝**気に入ったもの**（作品で使うかは別）。軸は**今は 1 つ**
- 段階評価（星）は**入れない**
- 判断の単位は 1 枚ずつとまとまりの**両方**
- キーボードは**補助**（必須にしない）
- 注記は**矩形と楕円**。座標は **0〜1 の割合**。書き出しは**座標 JSON** と**囲んだ範囲ちょうどの切り出し**
- 比較で作るのは 並べる / 来歴の差分表 / 差分ヒートマップ / 同期ズーム / 似ている順。
  **点滅・スワイプ・重ねるは後から足せる**ようにする（今回は作らない）

**エージェント**
- 要求は HTTP API（`POST /api/review-requests`）。**投げてすぐ返る**（判断を待たせない）
- エージェントは **API をポーリング**して結果を得る
- 要求に含める: 画像の一覧 / まとまりと選び方 / 見てほしい条件 / **AI の下書き判断** / どこから来たか / 応答に求めるもの
- **同じ対象なら新しい要求で上書き**（**画像の差し替えも可**）
- **AI の下書きと人の判断は両方を残す**
- 気づき方は**画面の件数とタブのタイトル**。音は使わない。トレイのアイコンも変わる
- さばくのは**要求の一覧画面**。認証は**付けない**

**生成の条件**
- **このツールは生成を実行しない。** 記録と再利用（コピー / ComfyUI で開く / **seed 違いのグラフ書き出し** / プリセット）
- プリセットは**人間が参照できればよい**（他のカットへの適用やエージェント向け API は作らない）
- 訳し直しは **ComfyUI の `TextGenerate`**（Ollama は今回使わない）
- 監視は**必要なときだけ手で開始**。ただし**結果の取り込みに使う**ので、書き出しには**印**を付ける
- モデルの同一性は `(名前, size, mtime)`。**任意で押せる**ようにフルハッシュも取れるようにする

**消す**
- **本当にファイルを消したい場面がある**（ボツの完全削除 / 容量 / 失敗した大量生成 / 重複）
- 確認は**一覧を見せて 1 回だけ**。その代わり**削除後 5 分間は取り消せる**
- 一括削除の指定は フォルダ・まとまり単位 / 検索結果・絞り込み単位 / 手で選んで一括

## 5. 見てほしいこと

### 5.1 決定との矛盾（最優先）

  特に「連携しない」と決めたのに連携を前提にした記述が残っていないか、
  「実行しない」と決めたのに実行を前提にした API や手順が残っていないか。

  外部契約の enum と、文書の説明と、例が一致しているか。

### 5.2 設計そのものの穴

- **要件（`design.md` §1 の R1〜R13）に対して、設計が足りているか。** 抜けている要件はないか。
  逆に、要件に無いのに作り込んでいる部分（過剰設計）はないか。
- **データモデル（§5）** で矛盾や破綻が起きないか。特に:
  台帳（`decision`、追記のみ）と現在値（`asset.review_state`）の二重持ち。
  内容（`sha256`）を正体にして場所を従属させた設計。
  `review_request` の上書き（`superseded_by`）と画像の差し替え。
- **API（§6.1）** に足りない口、重複した口、責務が混ざった口はないか。
- **外部契約（§6.2 と schema）** は、他ツールにとって十分か。余計なものを漏らしていないか。
  契約に**入れていないもの**（要求の状態、画像の種別）の判断は妥当か。
- **工程（§14）** の分け方と順序。各段の完了条件は、本当に確かめられる形になっているか。
- **性能（§12）** の目標値は、根拠のある実測に基づいているか。達成できない目標はないか。
- **リスク（§15）** に漏れている危険はないか。

### 5.3 安全（ここは厳しく見てください）

- **削除の設計**（`duplicates-deletion-backup.md` §3）: 確認 1 回 ＋ 5 分の取り消しで足りるか。
  保留領域（同一ボリュームへの `os.replace`）の置き場所、アプリが閉じている間に窓が切れた場合、
  取り消しの失敗、といった穴はないか。**利用者のファイルを失う経路**が残っていないか。
- **登録ルート外を触らない**規則が、実装として本当に守れる書き方になっているか。

## 6. 報告の形式

`docs/review-report.md` に、次の形で書いてください。

```markdown
# 設計点検の報告

- 点検した版: （ファイルの更新時刻など、分かる範囲で）
- 総合判定: 実装に進んでよい / 修正してから進む / 設計をやり直す

## A. 決定との矛盾（必ず直す）
| # | 場所 | 矛盾の内容 | なぜ困るか | 提案 |
| --- | --- | --- | --- | --- |

## B. 重大な問題（設計を変える必要がある）
（同じ表の形。番号は通し）

## C. 中程度（実装前に決めたい）
## D. 軽微（実装中でよい）
## E. 事実・前提の誤り
## F. 未確認のまま危険な箇所
## G. 依頼者への質問（判断が要るもの）
## H. 私が見落としている観点
## I. 設計書と実装のずれ（§5.7）
| # | 場所（設計と実装の両方） | ずれの内容 | どちらが正しいと思うか | 提案 |
| --- | --- | --- | --- | --- |
```

- **各項目に必ず「場所」を書く**（ファイル名と節番号、または行番号）。
- 「なぜ困るか」は、**実装が始まった後で気づいたときに何が起きるか**で書いてください。
- 提案は、**この設計の前提（§3 の決定）を変えずに済む形**を優先してください。
  前提を変える必要があるなら、そう書いてください。
- 問題が無いと判断した観点は、**「見た結果、問題なし」と 1 行で書いてください**（見落としと区別するため）。
- **1 回目の点検（`docs/review-report-deepseek.md`）と同じ指摘は繰り返さないでください。**
  既に直したものは `docs/review-triage.md` に仕分けがあります。**その仕分けが誤っている**と思うなら、
  そう書いてください（「却下されているが、実は直すべき」は重要な指摘です）。
- とくに **`docs/review-report-deepseek.md` の `H. 見落とし観点`** と、
  同報告が「自分は設計を書いた側と同系統なので判断が甘い」と申し送った点
  （`design.md` §12.1 の自己申告、`comparison.md` と `duplicates-deletion-backup.md` の相互参照）を
  重点的に見てください。

最後に、**あなたが最も重大だと思う 3 件**を順に挙げて、理由を 2〜3 文で書いてください。
そのうち少なくとも 1 件は、**1 回目の点検が見つけられなかったもの**にしてください。
