## B. 重大

### B-1. 起動に失敗しても 90 秒待つ（アイコンも窓も出さない）

- 再現（`startfail.log`）: `-DataDir` にファイルを渡す → 子は `db.py:891 open_db` で 1 秒以内に落ちる → トレイは**93 秒後に**「サーバが 90 秒で立ち上がりませんでした。ログの末尾: … `^^^^^^^^` … `File "…db.py", line 891, in open_db`」を出して終わる。その間、利用者にはアイコンも窓も見えない（ショートカットを押して何も起きない、に見える）。
- 原因: `Wait-ServerUp`（`tray.ps1:218-228`）が子の生死を見ない。
- 直し方: ループの中で `$State.Proc.HasExited` なら、すぐにログの末尾で失敗にする（A-2 と同じ 1 行）。ダイアログは規約 3 の 2 文（「サーバを起動できませんでした。」＋「`<リポジトリ>\.tray\server.err.log` を見てください。」）にして、トレースバックは「（詳細: …）」に入れる（D-3）

### B-2. 自分が起動したサーバが落ちても知らせない

- 再現（`crash.log`）: 本体を `taskkill /F`（落ちたことにする）→ 24 秒後: ツールチップ「image-reviewer（停止中）」・アイコン `down`・メニューは「起動する」。**バルーンは出ない**（`Send-TrayNotifications` は `state -ne 'up'` なら何もしない。`tray.ps1:898`）。
- アイコンの `down` は枠の色が (120,126,136) で、ふつう (71,85,105) と **16 px ではほぼ同じ**（`icons/s16-dark.png`）。
- 家風「黙って失敗しない」と `design.md` §4.1「黙って死なない」に対して、**起動の後に死ぬ道が設計にも実装にも無い**。
- 直し方: `own` のときに `up → down` に変わったら、Warning のバルーンを 1 つ出す（「サーバが止まりました。トレイの「起動する」で起動し直せます。」）。`down` のアイコンは形で区別する（例: 斜線か × の印）

## C. 中程度

### C-1. 起動の直後のバックアップの失敗はバルーンが出ない

`Refresh-Tray` の最初の 1 回は `-Quiet`（`tray.ps1:994`）で、次の回からは「前は失敗していなかった」が要る（`:899`）。サーバの日次は**起動した直後に 1 回見る**（`app.py:160-161`）ので、**起動の時点で失敗していれば、一番よくある失敗の時刻にバルーンが出ない**（`backupfail.log` に「知らせ:」が無い）。`README.md` の「**バックアップに失敗したとき**はバルーンで知らせる」と食い違う。直し方: 最初の 1 回でも `backup_failed` だけは知らせる。

### C-2. サーバが生きていて遅いと、1 回の確認で UI が 15 秒止まる（穴 3 より重い）

`freeze2.log`: `/api/health` は 0.1 秒で 200、残りの 3 つが 5.0 秒ずつ時間切れ → `Get-TraySnapshot` は **15.0 秒**。その間メニューは押せない。結果は `state=up`・ツールチップ「image-reviewer（稼働中）」で、**件数が黙って消える**（`requests = -1` を出さないだけ）。直し方: 3 つの口の時間切れを 2 秒にし、1 つでも落ちたら残りを打たずに前の値を「（確かめられませんでした）」付きで出す。根本は背景スレッド（穴 3 の申し送りどおり）。**サーバ側のどの操作が口を 5 秒以上塞ぐかは確かめていない**（H）

### C-3. 終了と再起動が、死んだ踏み台の PID に `taskkill /T /F` を打つ

`crash.log`: 本体を止めると踏み台も終わる（`stub alive after body kill: False`）。それなのに「起動する」は `サーバを止めます（pid 2916。木ごと）` を打つ。`ownstranger.out` でも死んだ 28168 に 2 回打っている。`Get-OwnServerPids`（`:338`）は踏み台の生死も同一性も確かめない。**Windows は PID を使い回す**ので、その間に別のプロセスが同じ番号を取っていれば、**その木ごと強制で止める**。使い回しそのものは再現していない（H）。直し方: 起動の直後に `$proc.Handle` を 1 回読んでハンドルを持たせ（持っている間は PID が再利用されない）、`-not $proc.HasExited` のときだけ撃つ。

### C-4. 自分のサーバが落ち、他人が同じポートで立つと、メニューと窓が誤った案内をする

`ownstranger.out`:

- ツールチップは「image-reviewer（稼働中）」、メニューは「再起動する」「終了する（サーバも止める）」が押せる（**どちらも、もうそのサーバを止めない**）。
- 「再起動する」は 20 秒待ってから「サーバを止められませんでした。**タスクマネージャーで python を終わらせてから**、もう一度試してください。」を出し、「終了する」も同じ案内を出す。**止められなかった相手は他人のサーバ**なので、その案内は他人を止めさせる。
- 他人のサーバそのものは止めていない（M3 の安全は成り立つ）。

直し方: 確認のたびにポートの pid が自分の本体と違えば `Mode` を `attach` 扱いにして、メニューの語を変える（A-2 の直しと同じ判定を見張りでも使う）。

### C-5. 実データの形では「取り消せる削除あり」のアイコンが常に点く

`rA`（実データの複製）でのツールチップは「image-reviewer（稼働中）、最近の削除 194」、アイコンは `delete`。`/api/pending-deletes` は段 1〜3 を返す（`api/deletions.py:97-103`）。利用者が 194 行を片付けるまで（実体のある 1 行は片付けられないので、その 1 行が残る限り）**印が消えない**。「変わったときに知らせる」印が常に点いていると、要求の印（`both`）との区別も弱くなる。G-1。

### C-6. （段をまたぐ）pytest は、呼んだシェルの `IMAGE_REVIEWER_DATA` をそのまま使う

`tests/conftest.py:49` は `os.environ.setdefault(...)` である。安全網の env を置いた親から pytest を回すと、**テストが安全網のフォルダに `db.sqlite3` を作った**（17:53:38）。`test_pytest_always_has_a_data_dir_that_is_not_the_real_one` は 3 回とも落ちた（`regress.log`）が、**その時点で前のテストは既にそのフォルダを開いている**。親が `.data` を指していれば、実データを開いた後で 1 件落ちるだけになる。A-1 と同じ型（「引き継いだ環境に頼る」）。直し方: `setdefault` を**上書き**にするか、既定の `.data` を指していたら `pytest_configure` で `pytest.exit`。
