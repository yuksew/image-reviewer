# 重複・削除・バックアップの設計

画像を溜めると必ず起きる 3 つ（同じ絵が増える / 消したくなる / 壊れる）を設計する。

- 版: 0.1（実装前）
- 前提: [`design.md`](design.md) §5（データモデル）・§12（性能）、[`comparison.md`](comparison.md) §4（知覚ハッシュ）
- **この文書は `design.md` §5.1 の同一性の設計のうち、知覚ハッシュと `seed` の持ち方（§1.3）、
  パスの中身が入れ替わったときの扱い（§1.4）だけを改訂する。** 表そのものの定義は `design.md` §5.1 が正。理由は §1。

---

## 1. 同一性は「内容」で決める（データモデルの改訂）

### 1.1 なぜ変えるか

`design.md` §5.1 は「1 パス = 1 `asset`」としていた。これだと:

- 同じ画像が 2 か所にあると 2 行になる → **同じ絵に 2 つの判断が付く**（どちらが正か分からない）
- ファイルを移動するとパスが変わる → 別の行として増える → **判断が切れる**
- 重複の整理が「行を消す」作業になる → 判断の履歴が壊れる

そこで **正体は内容（`sha256`）、場所は従属**とする。理由はこのツール単独で完結している:
「同じ絵に 2 つの判断が付く」「移動で判断が切れる」という 2 つの困りごとを、
**同一性を内容に置く**ことで同時に消せるからである。パスは「その内容が今どこにあるか」にすぎない。

### 1.2 実測した根拠（ハッシュの費用）

内容を正体にすると、走査時に全ファイルをハッシュすることになる。**実測した:**

| 項目 | 実測値 | 1 万枚（**11.1 GB** = 1.11 MB/枚）の見込み |
| --- | --- | --- |
| SHA-256（Python、1MB ずつの読み） | **399 MB/s**（300 枚 410 MB を 1.03 秒） | **約 28 秒** |
| PNG のチャンク走査（256 KiB 上限） | **24,719 枚/秒** | 0.4 秒 |
| サムネイル生成（1 スレッド、256px） | 36 枚/秒 | 4.6 分（並列でさらに短い） |

→ ハッシュは**走査の一部として実行してよい費用**（1 万枚で 28 秒）。
「ハッシュを計算するまで画像が見えない」という不便も起きない。
**2 回目以降の走査はさらに安い**:（パス・サイズ・mtime）が変わったファイルだけハッシュすればよい。

> **点検で正した数字**: 以前は 1 万枚を **13.7 GB** として 34 秒としていた。これは
> ハッシュを測った 300 枚（410 MB、1.37 MB/枚）の比率をそのまま外挿した値で、
> 全 1,028 枚の平均（1.11 MB/枚 → 11.1 GB）より 24% 大きい。**全体の平均を使う**。
> 実測の出所は [`metadata-findings.md`](metadata-findings.md) §7。

### 1.3 改訂後のスキーマ

**`asset` / `asset_location` の定義は [`design.md`](design.md) §5.1 が正。** この文書は表を再掲しない
（`kind`（生成物 / 参考資料 / 写真）・`source_url`・`ref_tags` は §5.1 が持つ。`source` の値集合も §5.1 に一本化する）。
この文書が §5.1 に足す差分は、次の 2 つだけ:

1. **知覚ハッシュと `seed` は TEXT で持つ。** SQLite の `INTEGER` は**符号付き 64bit**
   （最大 9,223,372,036,854,775,807）なので、符号なし 64bit の値（`phash` は約 50% の確率で最上位ビットが立つ。
   `seed` は `0xFFFFFFFFFFFFFFFF` まで取りうる）は入らない。
   - `asset.phash` / `asset.dhash`: **16 文字の小文字 16 進の TEXT**（`design.md` §5.1 の `phash INTEGER` を
     この形に読み替える）。**ハミング距離の計算は Python の任意精度整数**で行い、
     16 進の文字列を `int(hex, 16)` に直してから数える。帯の値（§2.2）も **2 文字の 16 進の TEXT** にする。
     帯の完全一致は**文字列の比較**でよい。
   - `seed`: **TEXT（10 進の文字列）**で持つ（上位ビットが立つ値を取りうるため）。並べ替えの扱いは
     `design.md` §5.1・§5.6 が正で、**この文書では変更しない**。
2. **`location_history` を足す**（§1.4。同じパスが別の内容に入れ替わったことの記録）。

```sql
-- パスが「別の内容に入れ替わった」ことの記録（§1.4）。古い asset_location を消す前に書く
CREATE TABLE location_history (
  id                   TEXT PRIMARY KEY,
  asset_id             TEXT NOT NULL REFERENCES asset(id) ON DELETE CASCADE,  -- 以前そのパスにあった内容
  path                 TEXT NOT NULL,      -- 入れ替わったパス
  size                 INTEGER NOT NULL,   -- 入れ替わる前の実測
  mtime_ns             INTEGER NOT NULL,   -- 入れ替わる前の実測
  first_seen_at        TEXT NOT NULL,
  last_seen_at         TEXT NOT NULL,
  replaced_by_asset_id TEXT REFERENCES asset(id),  -- 新しい内容（同じ走査で分かるとき）
  replaced_at          TEXT NOT NULL
);
CREATE INDEX ix_loc_hist_path ON location_history(path, replaced_at DESC);
```

- `location_history` は**履歴専用**で、「今どこにあるか」ではない。現在の場所は `asset_location` だけが持つ。
- `asset_location` の **`UNIQUE(path)`（`design.md` §5.1 の `ux_loc_path`）はそのまま残す**。
  これを成り立たせるのは索引ではなく**§1.4 の順序**（古い行を消してから新しい行を入れる）である。
  `ix_loc_hist_path` は「このパスは前に何だったか」を引くためのもので、`ux_loc_path` を置き換えない。
- `asset.sha256` への `UNIQUE` により、**完全重複は自動で 1 行にまとまる**（`design.md` §5.1。§2.1）。
- 取込モード（`design.md` §5.1）の実体は `<data>/library/<sha256[0:2]>/<sha256>.<ext>` に置き、
  `asset_location.kind='managed'` として同じ表に入れる。**参照と取込が同じ画像なら 1 行 2 場所**になる。
- `asset_location.missing_at` は「消えた」ではなく「見つからない」。判断（`decision`）は `asset` に付くので**残る**。

### 1.4 走査の手順（差分）

```
1. ルートを os.scandir で再帰する
2. 画像らしくないファイルを除外（拡張子 → マジックナンバー）
3. 既存の asset_location と突き合わせる:
   (path, size, mtime_ns) が同じ  -> 何もしない（last_seen_at だけ更新）
   パスは同じで size/mtime が違う -> ハッシュを計算し直す（→ 4b へ）
   新しいパス                     -> ハッシュを計算する（→ 4a へ）
4a. ハッシュが既存の asset にあれば asset_location を足すだけ（重複として記録）
    無ければ asset を新規作成し、PNG のメタデータ抽出と pHash を背景ジョブへ積む
4b. パスの中身が変わっていたら（同じパスに別の内容）:
    (1) そのパスの古い asset_location 行を消す（古い asset からパスが外れる）
    (2) location_history に「このパスは別の内容に入れ替わった」ことを書く
        （asset_id=古い内容 / path / 入れ替わる前の size・mtime_ns / first_seen_at / last_seen_at /
          replaced_by_asset_id=新しい内容 / replaced_at）
    (3) 4a と同じ規則で、そのパスを新しい asset に付け直す（新規なら asset を作る）
5. 走査で見つからなかった asset_location に missing_at を立てる（行は消さない）
   - 「この走査の範囲に入っているか」の判定は is_under（区切り文字の単位で比較し、
     `C:\img` が `C:\img2\x.png` を飲み込まない）で行う。これは**走査の範囲を決めるためだけ**の判定で、
     削除の可否判定ではない（§3.2 の 1）。
```

- **`UNIQUE(path)`（`design.md` §5.1 の `ux_loc_path`）はこの順序で守る。** 同じパスに 2 行目を入れることは
  できないので、必ず「古い行を消す → `location_history` に書く → 新しい行を入れる」の順で行い、
  1 つのトランザクションにする（途中で落ちても「パスがどの内容にも属さない」状態を残さない）。
  旧版の「別の `asset` を作って同じパスに場所を足す」は、初回の再走査で `UNIQUE` 違反になる**誤り**。
- **(注)** 再計算したハッシュがそのパスの古い `asset` と同じなら、内容は変わっていない（`mtime` だけが動いた）。
  `asset_location` の `size` / `mtime_ns` / `last_seen_at` を更新するだけで、入れ替えも `location_history` も行わない。
- **古い `asset` は同一性を保つ。** 判断（`decision`）・来歴・**他の場所はそのまま残る**。
  他の場所が 1 つも残らなければ、`asset` は**行として残したまま**「生きた場所が 1 つも無い」状態になる。
  これは `asset_location.missing_at` を立てたときと**同じ扱い**（§4 の「全部の場所が切れた」）で、
  **行は消さない**（判断は画像より長く生きる。§3.2 の 4）。
- トランザクションは 500 件ずつ。`INSERT ... ON CONFLICT(path) DO UPDATE`。
- 拡張子とマジックナンバーが食い違う場合はマジックナンバーを優先（`design.md` §7.1）。
- 進捗は SSE（`design.md` §12.2）。

## 2. 重複

### 2.1 完全重複（同じバイト）

`sha256` が同じもの。`design.md` §5.1 の `asset.sha256` の `UNIQUE` により**構造的に 1 行**になるので、
検出は「2 か所以上にある `asset` を引く」だけ。

```sql
SELECT asset_id, COUNT(*) AS n FROM asset_location
WHERE missing_at IS NULL GROUP BY asset_id HAVING n > 1;
```

画面では「同じ絵が 3 か所」と出し、**代表を 1 つ選んで他を外す**（§3.1 の段 1〜3）。
**外しても内容は失われない**（代表が残る）ので、この操作は安全側に倒せる。**代表というコピーが残る限り、
コピーの実削除（段 3）も軽い確認で進められる**（§3.2 の 3）。
（旧版は「§4 の段 1 または段 2」と、段の定義が無い §4 を指し、段 3 を除外していた。参照と範囲を直した。）

### 2.2 準重複（再エンコード・リサイズ・メタデータ違い）

バイトは違うが同じ絵。`phash` のハミング距離で見つける。

- 候補の絞り込み: 64bit を **4bit × 16 本の帯**に分け、帯ごとに索引する（`phash_band` 表）。
  **距離 ≤ 7 なら 8 本のうち少なくとも 1 本は一致する（距離 k は最大 k 本の帯しか食い違えないため）。**
  しきい値 ≤ 6 はこれを満たす。
  これで 1 万枚でも総当たり（5×10⁷ 回）を避けられる。
- **旧版の「16bit × 4 帯なら距離 ≤ 6 で必ず 1 帯は一致する」は誤り**（保証できるのは距離 ≤ 3 までだった）。
  帯を 4bit × 16 本にしたのはこの修正のため。4 帯の主張をここへ戻さないこと。
- 確定: 候補の組だけハミング距離を計算し、≤ 6 なら準重複とする。SSIM も併せて出す。
  ハミング距離は 16 進の TEXT を `int(hex, 16)` に直し、**Python の任意精度整数**で数える（§1.3）。
- 近い組は**まとまり（`review_group`, `kind='duplicate'`, `policy='pick_one'`）**にする。
  → **重複の整理は、このツールのまとまりレビューの仕組みをそのまま使う**。
  重複専用の画面も概念も増やさない（1 枚をキープして他をボツ / 全部ボツ / 保留が同じ操作でできる）。

```sql
CREATE TABLE phash_band (
  asset_id TEXT NOT NULL REFERENCES asset(id) ON DELETE CASCADE,
  band     INTEGER NOT NULL,   -- 0..7
  value    TEXT NOT NULL,      -- その帯の 8bit を 16 進 2 文字（小文字）で持つ（§1.3）
  PRIMARY KEY (asset_id, band)
);
CREATE INDEX ix_phash_band ON phash_band(band, value);   -- 帯の完全一致は文字列比較
```

### 2.3 同一生成の別出力

同じ `provenance.seed` + 同じプロンプトで保存だけ違うもの。§2.2 の距離で拾えるが、
来歴が一致するので**来歴でも検出できる**（`seed` + `model` + `positive_literal` が同じ）。
画面には「同じ生成条件」として出す。これは重複ではなく**同じ絵の別保存**であることが多い。

### 2.4 誤検出を前提にする

知覚ハッシュは「別の絵を同じと見なす」ことがある（構図が同じ別キャラなど）。
そこで:

- **自動で消さない・自動でまとめない。** 候補を出すだけ。
- 「別物として確定」を押した組は `duplicate_exclusion` に記録し（`(min,max)` に正規化）、以後出さない。
  **解除する口も用意する**（間違えたときに戻せないと、その組が二度と出なくなる。点検 C10）。
- しきい値は実データで調整する（`design.md` §16）。初期値は pHash ≤ 6 / SSIM ≥ 0.95。

## 3. 削除

### 3.1 3 段階（取り返しのつかなさの順）

| 段 | 名前 | ファイル | DB | 取り消し |
| --- | --- | --- | --- | --- |
| 1 | **カタログから外す** | 触らない | `asset.deleted_at` を立てる（論理削除） | いつでも戻せる |
| 2 | **ゴミ箱へ移す** | `<data>/trash/<日付>/` へ移動 | 論理削除 ＋ 元のパスを記録 | 戻せる（元の場所へ） |
| 3 | **実ファイルを消す** | 消す（保留領域を経由） | `asset_location` を消す。`asset` は判断を残して論理削除 | **削除後 5 分間だけ戻せる**（§3.4） |

実ファイルを消したい場面（利用者が挙げた 4 つ）:

- ボツにしたものを完全に消したい
- 容量を空けたい
- 失敗した大量生成をまとめて消す
- 重複した画像を消す

- **既定は段 1。** 一覧から消えて、判断と来歴は残る。段 2・段 3 は明示的に選んだときだけ進む
  （どちらも同じ一覧から選ぶ。段 2 なら元の場所へ戻せる）。
- 段 3 は**取り返しがつかない**ので、確認を重くする代わりに**安全網**を置く:
  - 確認は**1 回だけ**。その画面に**消す対象の一覧そのもの**を出す（1 件ごとにパスとサイズ、
    上に件数と合計バイト数）。再確認や件数の打ち込みは求めない。
  - ただし、消そうとしているものが**最後の 1 つ**（生きた場所がその 1 つだけ）のときだけ、確認を重くする。
    内容そのものが失われることを画面に明示する（§3.2 の 3）。
  - 実行してもファイルはすぐには消さない。同じボリューム上の保留領域へ移し、
    **削除後 5 分間は取り消せる**（§3.4）。5 分を過ぎたら保留領域ごと消える。
    **この 5 分は「アプリが動いていた時間」で数える**（スリープ・休止・終了の間は進まない。§3.4）。
- 段 3 でも `deletion_log` に記録を残す。**台帳は削除後も消さない**（§3.2 の 4）。

```sql
CREATE TABLE deletion_log (
  id        TEXT PRIMARY KEY,
  asset_id  TEXT,          -- 内容（消しても残す。内容が分からなくなっても id は残す）
  path      TEXT,          -- 対象のパス
  stage     INTEGER NOT NULL,   -- 1 | 2 | 3
  from_path TEXT, to_path TEXT, -- 段 2 の移動元・移動先
  hold_path TEXT,          -- 段 3 の保留領域（<data>/pending-delete/<削除ID>/）
  remaining_sec INTEGER,   -- 段 3: 取り消せる残り時間（秒。既定 300）。単調時計で減らす（§3.4）
  purge_at  TEXT,          -- 段 3: 画面に出す目安の壁時計時刻。NULL は「自動では消さない」の印（§3.4）
  restored_at TEXT,        -- 段 3: 取り消した時刻（取り消したら purge_at と remaining_sec を無効にする）
  reason    TEXT,
  actor     TEXT NOT NULL,
  at        TEXT NOT NULL
);
CREATE TABLE duplicate_exclusion (
  -- **順序に依らず同じ組を指すよう、(小さい方, 大きい方) に正規化して入れる**（点検 C10）
  a_id TEXT NOT NULL, b_id TEXT NOT NULL,   -- a_id < b_id を必ず満たす
  reason TEXT, actor TEXT NOT NULL, at TEXT NOT NULL,
  PRIMARY KEY (a_id, b_id),
  CHECK (a_id < b_id)
);
```

- **解除できること（点検 C10）**: 「別物として確定」を間違えたときに戻せないと、その組は二度と候補に出ない。
  `DELETE /api/duplicates/exclude {a_id, b_id}` を必ず用意し、解除したことは
  `deletion_log` ではなく `duplicate_exclusion` の削除で表す（監査は `actor` / `at` を見る）。
  正規化（`a_id < b_id`）を忘れると、`(A,B)` と `(B,A)` が別行になり、
  **確定したのに候補に出続ける**（`CHECK` で機械的に防ぐ）。

### 3.2 安全規則（破ったら壊れるものを先に書く）

1. **触ってよいのは、登録済みの `asset` の `asset_location` に実在するパスそのものだけ。**
   比較は、対象のパスと `asset_location.path` の**両方**を `normalize_path(p)` =
   `os.path.normcase(os.path.realpath(p))` に通し、**完全一致**で行う。
   `normcase` は Windows の大小文字を、`realpath` はシンボリックリンク／ジャンクションを揃える
   （この環境には `custom_nodes\illust_tagger` のようなジャンクションがある。実在する）。
   プロトタイプの `src/image_reviewer/store.py` の `normalize_path` がこの意味の実装で、
   **この文書はその意味をそのまま要求する**。
   - **前方一致は使わない。** 前方一致は `C:\img` と `C:\img2\x.png` も一致させてしまう。
     削除の可否は**完全一致だけ**で決める。
   - **`<data>/library` と `<data>/pending-delete` は暗黙の対象**として明示的に許す
     （取込モードの実体と、段 3 の保留領域。どちらも「登録された場所」と同じ扱いにする）。
   - **区切り文字の単位で「下にあるか」を見る判定（`is_under`）は、走査で `mark_missing` を立てる範囲を
     決めるときだけに使う**（§1.4 の 5）。削除の可否判定には使わない。`is_under` は文字列の前方一致ではなく
     パスの構成要素の単位で比べる（`C:\img` は `C:\img2\x.png` を飲み込まない）。
   - **点検で見つかった誤り（旧 §3.2 の 1）**: 旧規則は「登録済みルートの外は絶対に触らない（`realpath` ＋
     登録ルートの前方一致）」だった。**ルートを持つのはフォルダ走査だけ**で、D&D・URL・クリップボード・要求で
     登録した画像と `<data>/library` の取込実体には**ルートが無い**。そのまま実装すると、これらは段 3 で必ず
     「ルート外」として拒否される（＝消せない）か、実装者が規則を緩めて**任意のパスを消せる**ようにするかの
     どちらかになる。規則を「登録された場所そのものだけを触る」に置き換える。
2. **ハッシュ確定後に中身が変わっていたら中断する。** `size` / `mtime_ns` が登録時と違えば、
   別のファイルを消そうとしている。中断して利用者に出す。「中断」は**対象 1 件**の話で、
   一括削除では**その項目だけを飛ばして残りを続ける**（§3.5）。
3. **同じ内容が複数の場所にあるとき、最後の 1 つだけ重い確認にする。**
   - **他のコピーがある場合**: そのコピーの実削除は**軽い確認**（§3.1 の 1 回の確認）で段 3 に進める。
     消しても内容は他の場所に残るので、失われるのは「その場所という 1 つの在りか」だけである。
   - **最後の 1 つ**（`missing_at` が立っていない `asset_location` が 1 つだけ）:
     消せば**内容そのものが失われる**ので、段 3 には**重い確認**を要求する。§3.1 の 1 回の確認に加えて、
     「これが最後の 1 つで、内容そのものが失われる」ことを画面に明示する（確認の具体的な見た目は
     [`frontend-design.md`](frontend-design.md) が正。この文書は追加の条件だけを課す）。
   - **点検で見つかった誤り（旧 §3.2 の 3）**: 旧規則は「最後の 1 つ以外は段 2 まで許す。最後の 1 つを消すときだけ
     段 3 を要求する」だった。字義どおりなら、**最も安全に消せるもの（残るコピー）を段 3 から締め出し、最も危険な
     もの（最後の 1 つ）だけを実削除に進める**ことになる（規則が逆向き）。決定「重複を整理して本当に消す」とも
     矛盾するので、意図に合わせて書き直す。
4. **判断（`decision`）は消さない。** 段 3 でも `asset` の行と台帳を残す。
   「なぜこれを落としたか」は画像より長く生きる。
5. **走査中は削除しない。** 走査ジョブと削除を同時に走らせない（同じファイルを掴み合う）。
6. **一括削除の選び方は 3 つだけ。** (a) フォルダやまとまり単位、(b) 検索結果・絞り込み単位、
   (c) 手で選んで一括。いずれも**対象を preview で凍結し、件数と合計バイト数を画面に出してから**実行する
   （§3.5。§3.1 の 1 回の確認）。**実行時に検索を引き直さない**（凍結した一覧だけを消す）。
7. **ゴミ箱の自動掃除は既定 30 日。** 掃除の前に `deletion_log` の一覧を出す。
   掃除は「段 3 の実行」なので、既定では自動にせず通知だけにする（利用者が決める）。
8. **保留領域（`<data>/pending-delete/`）は 5 分の窓のためだけに使う。** 窓（**アプリが動いていた時間**。§3.4）を
   過ぎたら必ず消す。ただし**起動時には消さない**（取り残しの回収もしない）。閉じている間は時間が進まないので、
   起動した瞬間に「期限切れ」になる行は無い。バックアップにも含めない（一時領域）。

### 3.3 ゴミ箱

- `<data>/trash/<YYYYMMDD>/<sha256[0:2]>/<元のファイル名>` に置く。
- 同名の衝突は `<名前>.<連番>.<拡張子>` にする。
- 元のパスは `deletion_log.from_path` に残すので、**元の場所へ戻せる**。
- ゴミ箱の中身は一覧に出さない（専用の画面で見る）。

### 3.4 最近の削除（削除後 5 分間の取り消し）

段 3 の確認を 1 回だけにした代わりに、**削除の直後 5 分間は取り消せる**ようにする。

- **削除の実体は「移す」＋「後で消す」。** 段 3 の実行は、バイト列を
  `<data>/pending-delete/<削除ID>/` へ移すところまでを行い、**即座に unlink しない**。
  - 保留領域は**対象と同じボリューム**に置く。同一ボリュームなら `os.replace`（名前の付け替え）で済み、
    ファイルサイズに関係なく一瞬で終わる（コピーしない）。**別ボリュームに置いてはならない**
    （コピーになり、大きいファイルで待たされ、途中で失敗すると中途半端になる）。
    既定は `<data>/pending-delete/<削除ID>/`。`<data>` が対象と別ボリュームにある場合は、
    **対象側のボリューム**に保留ディレクトリを作る（その場合の命名と場所は実装時に決める。**未確認**）。
  - `<削除ID>` は `deletion_log.id`。移動先は `deletion_log.hold_path`、**残り時間は
    `deletion_log.remaining_sec`**（秒。既定 5 分 = 300）に書く。`purge_at` は画面に出す**目安の壁時計時刻**
    （削除時刻 + 5 分）で、**`NULL` は「自動では消さない」の印**（下の取り消し失敗）。**消すかどうかの判定は
    `remaining_sec` で行い、`purge_at` では判定しない。**
- **5 分間は「最近の削除」に出し続ける。** 消した行は一覧から消さず、`最近の削除` の状態で
  **残り時間つき**に出す（例: 「あと 3:12」）。残り時間は `remaining_sec` から出す。
- **取り消しは、元のパスを上書きしない。** 取り消しを押したときの手順:
  1. `os.path.exists(元のパス)` を **`os.replace` の直前に**確かめる。判定と置き換えの間に別のプロセスが
     ファイルを作りうるので、この検査は「実務上差が出る程度に原子的」でよい（完全な原子的保証はしない。**未確認**）。
  2. **空いていれば** `os.replace` で元のパスへ戻し、`restored_at` を立てて `asset_location` を復活させ、
     `purge_at` と `remaining_sec` を無効にする（行は取り消し済みとして残す）。
  3. **埋まっていれば戻さない。** 「元の場所に別のファイルがあります」と出し、**別名で戻す**
     （`<名前>.<連番>.<拡張子>`）かを尋ねる。選ばれたらその名前で戻す。**決して上書きしない**
     （利用者が 5 分の間に置いた別のファイルを、取り消し操作で壊さない）。
- **取り消し自体が失敗したとき**（`os.replace` の失敗、別名での復帰の失敗のどちらも）:
  ファイルは**保留領域に残したまま**にし、`deletion_log` の行も `restored_at` も書かずに残し、
  **`purge_at` を `NULL` にして、この行を自動削除の対象から完全に外す**。`remaining_sec` ももう減らさない。
  行は「最近の削除」に**「戻せませんでした」**の状態で残り、**利用者が明示的に「消す」を選ぶか、
  もう一度「戻す」を試すまで、このツールはこのファイルに触らない。** 黙って再試行しない。
  画面に「戻せませんでした。ファイルは保留場所に残っています」と出し、もう一度試す導線を出す。
  - **点検で見つかった誤り（旧 §3.4 の取り消し失敗）**: 旧版は「`purge_at` をいったん未来へ延ばす」としていたが、
    **いつまで延ばすかが書かれていなかった**。延ばした先で自動削除が走れば、「戻せませんでした」と出したものを
    後で黙って消すことになる。`NULL` にして自動削除から外す。
- **窓は「アプリが動いていた時間」で数える。** 背景のタイマーは既定 30 秒間隔で動き、前回の確認からの経過を
  **単調時計（`time.monotonic`）**で測って `remaining_sec` から引く。**スリープ・休止・ログオフ・終了の間は
  時間が進まない**ので、`remaining_sec` は減らない。
- **`remaining_sec <= 0` になったら消す。** 消すのは `hold_path` だけで、消した後も `deletion_log` の行は
  **残す**（`hold_path` を「消えた」印にする）。**`purge_at IS NULL` の行は対象外**（自動では消さない）。
  - **点検で見つかった誤り（旧 §3.4 の窓の数え方）**: 旧版は `purge_at <= now`（**壁時計**）で判定していた。
    夜の作業中に席を外して PC がスリープすると、復帰した瞬間にタイマーが保留領域を消してしまう。
    「削除後 5 分間は取り消せる」が、利用者が画面を見ていられた 5 分ではなく、**機械の時計の 5 分**になっていた。
- **再起動したとき。** 起動時は**残り時間（`remaining_sec`）をそのまま引き継いで**「最近の削除」に戻し、
  タイマーを張り直す（保留領域はディスク上にあるので、そのまま取り消せる。**引き継ぐ値は保存した `remaining_sec`
  だけで、減算の基準になる `time.monotonic` は起動のたびに取り直す**）。**起動時には絶対に消さない**
  （保留領域の回収も、期限切れの処理も行わない）。**`purge_at` が `NULL` の行は「戻せませんでした」のまま戻し、
  タイマーの対象にはしない**（利用者が明示的に触るまで放置する）。
- **窓が切れている間にアプリを閉じていたとき。** **時間は進んでいない。** 閉じている間はアプリが動いていないので、
  `remaining_sec` は閉じたときのまま残る。起動すると**その残り時間から続き**、利用者は残りの窓をそのまま使える。
  - **点検で見つかった誤り（旧 §3.4 の「閉じていた間」）**: 旧版は「起動時に `purge_at` が過去の行を見つけたら、
    その場で保留領域を消して削除を完了させる（もう戻せない）」としていた。これは壁時計で数えていたための帰結で、
    **「アプリが動いていた時間で数える」と両立しない**。閉じている間は時間が進まないので、起動時に期限切れになる行は無い。
    クラッシュなどで `remaining_sec` が 0 のまま残った行だけは、**起動時には消さず**、タイマーの最初の確認で消す
    （**未確認**: この 1 回の猶予を画面でどう見せるかは決めていない）。
- 窓は既定 **5 分**（利用者が選んだ値。`remaining_sec` の初期値）。設定で変えられる
  （`0` にすると保留領域を使わず即時削除。**勧めない**）。

画面に出る合図は**トレイアイコンの変化とタブタイトルの件数**だけにする。
だからこそ `最近の削除`（残り時間つき）は**目に入る場所**に常設する。ここが見えないと
5 分の窓は使えない（ウィンドウを閉じていても取り消せるよう、トレイから開けるようにする）。

**画面とトレイの設計はこの文書が持たない。** 常設の入口の位置・見た目・トレイのメニュー項目は
`design.md` §4.1・§11 と [`frontend-design.md`](frontend-design.md) が正である。
この文書が要求するのは 1 点だけ: **取り消せる削除が 1 件でもある間は、残り時間が常に見える場所にある。**

### 3.5 一括削除は 2 段にする（凍結 → 実行）

一括削除は、**確認画面で見せた一覧と実行時に消える集合を一致させる**ため、凍結（preview）と実行の 2 段にする。
`design.md` §6.1 の `POST /api/locations/bulk-delete` はこの 2 段に合わせて改訂する（**機構の正は本節**）。

```
POST /api/locations/bulk-delete/preview
  {scope:{kind:'folder'|'group'|'query'|'assets', id?, query?, asset_ids?[]}, stage:1|2|3}
→ {preview_id,
   items:[{asset_id, path, size, mtime_ns}],   -- 凍結した対象（確認画面に出す一覧そのもの）
   count, bytes,
   frees:{bytes, at, note},                    -- stage ごとの「何がいつ空くか」
   expires_at}                                 -- 作った時刻 + 10 分

POST /api/locations/bulk-delete
  {preview_id, confirm:true}
→ {deleted:[{asset_id, path}],
   skipped:[{asset_id, path, reason}],         -- reason は 'changed' など
   count, bytes}
```

- **preview は対象を凍結する。** `scope` の解決（フォルダ／まとまり・検索結果・絞り込み・手で選んだ一括）は
  preview のときに **1 回だけ**行い、その結果（パス・`size`・`mtime_ns` の組）を `preview_id` に結びつけて保存する。
  **実行時に `scope` を評価し直さない。**
- **実行は凍結した一覧だけを消す。** 判断・タグ付け・別の削除がプレビューと実行の間に入っても、消える集合は
  確認で見せた一覧から動かない（§3.2 の 5 は走査しか排他していないので、ここで凍結して守る）。
- **実行の直前に 1 件ずつ `(size, mtime_ns)` を再照合する**（§3.2 の 2）。食い違った項目は消さずに飛ばし、
  `skipped` に「プレビュー後に内容が変わった」として返す。**残りの項目は消す**（1 件の食い違いで一括全体を
  止めない。§3.2 の 2 が止めたいのは「別のファイルを消そうとしている」その 1 件である）。
- **`preview_id` は短時間で失効させる（既定 10 分。設定で変更）。** 失効した `preview_id` での実行は
  **何も消さずに拒否する**（`409 preview_expired`）。画面には「確認した一覧の有効期限が切れました。
  もう一度プレビューしてください（対象は作り直します）」と出し、**古い一覧では消さない**。
  もう一度 preview を押すと新しい一覧が出るので、集合が変わっていれば**その差を見てから**確認できる。
- **何がいつ空くか**（`frees`）:
  - 段 1 は**何も空かない**（カタログから外すだけ。§3.1）。
  - 段 2 は対象を `<data>/trash/` へ移すので、**ゴミ箱の掃除（既定 30 日。§3.2 の 7）まで容量は空かない**。
  - 段 3 は保留領域へ移した後、**5 分の窓が過ぎた時点**で空く（§3.4。窓は**アプリが動いていた時間**で数える）。
- 一括削除の選び方は §3.2 の 6 の 3 つ。いずれも preview で**件数と合計バイト数**を出してから実行する
  （§3.1 の 1 回の確認）。
- **点検で見つかった誤り（旧 §6.1 の契約）**: 旧 `POST /api/locations/bulk-delete {scope:{kind:'query',…},
  confirm:true}` は `scope` を**実行時に評価**していた。確認で見せた一覧と実行時に消える集合を一致させる仕組みが
  無く、間に判断や別の削除が入れば集合は変わる。**見せていないファイルを消す経路**になるので、2 段に分ける。

## 4. 参照切れ（missing）と再リンク

画像は動く・消える。参照モードではこれが日常なので、**壊れないことを前提に設計する**。

| 状態 | 扱い |
| --- | --- |
| 走査で見つからない | `asset_location.missing_at` を立てる。行も判断も残す。一覧に「参照切れ」の印 |
| **走査で見つかった（戻ってきた）** | **`missing_at` を外す**（`last_seen_at` を更新）。**移動は `mtime_ns` を変えない**ので、同じパスへ戻した枚は走査の**早道**（`(size, mtime_ns)` が同じなら `register()` を呼ばない）に落ちる——ここで戻さないと**走査を何度回しても参照切れのまま**になる（**P8-6 の監査 C-1**。`Store.mark_seen()`。**印が立っていない行には書かない**。**段 2・3 の削除の途中の枚は戻さない**＝「最近の削除」から戻す） |
| 別の場所へ動いた | 同じ `sha256` なので、走査で新しいパスを見つけると**同じ `asset` に場所が増える**。判断は繋がったまま |
| 中身が変わった | ハッシュが変わる → 別の `asset` になる。`asset_location` の行は §1.4 の順で入れ替え、`location_history` に「入れ替わった」ことを残す。**元の判断は元の内容に残る**（これが正しい） |
| 全部の場所が切れた | `asset` は残す。詳細画面に「実体が見つかりません」と出し、再リンクを案内 |

再リンクの手段（設計では詳細画面から。**P8-6 で作ったのは口だけで、画面はまだ無い**）:

1. **近くを探す**: ファイル名で探し、ハッシュが一致すれば繋ぐ。（**P8-6 で実装**。探す範囲は
   **その参照切れを含む置き場から順に、見つからなければ残りの置き場**＝下の注記のとおり「同じルート内」では
   空振りになる。**P8-6 の監査 C-2** で 2 段にした＝306 MB の置き場を毎回は歩かない。歩いた範囲は
   応答の `folders` / `folders_skipped` / `found_in` で分かる）
2. **場所を指定**: ファイル選択で指定し、ハッシュを確かめてから繋ぐ。（**P8-6 で実装**。照合は `sha256` だけで、
   **pHash は使わない**——知覚ハッシュは「似た別の絵」を同じと見なすため）
3. **自動**: 走査のたびに、`missing_at` が立っている `asset` のハッシュと一致する新規ファイルを自動で繋ぐ。
   （**P8 では作らなかった**＝下の注記）

- **3 の「自動」は作らなかった**（P8-6 で作ったのは 1 と 2 だけ）。理由: ①**1 と 2 で合格の線 9 が通る**
  ②**走査が既に同じ `sha256` を同じ `asset` に登録する**ので、自動で繋ぐ余地は「走査していない置き場」だけ
  ③下の「**勝手に繋がない**」の規律（根拠は [`p8-6-relink.md`](p8-6-relink.md) §4.1-6）。
- **1 の「同じルート内をファイル名で探す」はそのままでは空振りになる**（②と同じ理由で、走査した置き場の中で
  動いた物は**走査の時点で既に繋がっている**）。**P8-6 は同じ名前を ①その参照切れを含む置き場
  ②残りの置き場の 2 段で探す形にした**（`p8-6-relink.md` §4.1-3 と **P8-6 の監査 C-2**。
  `path` を指定すればそのフォルダだけを歩く。**この挙動はテストで固定してある**）。

このツールも同じ立場を取る: **内容が違えば別物**。勝手に繋がない。
（**この 1 行が 3 の「自動」を作らなかった理由**。）

## 5. バックアップ

### 5.1 何を守り、何を守らないか

| 対象 | 守るか | 理由 |
| --- | --- | --- |
| 判断の台帳（`decision`）・理由マスタ | **必ず守る** | 人の作業の成果。再生成できない |
| カタログ構造（`folder` / `folder_member`） | **必ず守る** | 人が作った分類。再生成できない |
| 来歴のうち**捕獲した英訳**（`sidecar/`） | **必ず守る** | **PNG から取り直せない唯一のもの**（`metadata-findings.md` §2） |
| 来歴のその他（グラフ・パラメータ・日本語） | 守る（ただし PNG から取り直せる） | 手間を省くため |
| タグ（`wd14`） | 守る（再計算できるが時間がかかる） | 1 万枚で 1.5 時間 |
| サムネイル | **守らない** | 再生成できる（1 万枚 4.7 分） |
| pHash / dHash | **守らない** | 再計算できる（1 万枚 80 秒は [`comparison.md`](comparison.md) §7 の**未計測の見積り**） |
| 削除の保留領域（`pending-delete/`） | **守らない** | 一時領域。5 分の窓が過ぎれば消える（§3.4） |
| 画像の実体 | 参照モードでは**利用者の資産**（対象外）。取込モードは任意で含める | — |

- **`<data>` にあるだけでは守られない。** とくに `sidecar/`（捕獲した英訳）は `<data>` の中にしか無い。
  日次スナップショットを `<data>/backups/` に置くと、**守るものが、守られる対象の中に入る**（リスク 11 の循環。
  `<data>` を `git clean` や作り直しで失えば、DB も sidecar もバックアップも一緒に消える）。
  §5.2 の 1 でスナップショットの置き場を `<data>` の**外**に既定で置く。

### 5.2 手段

1. **日次の自動スナップショット（既定 ON）**
   - 起動時に 1 日 1 回、`sqlite3.Connection.backup()`（online backup API）で DB のコピーを取り、
     **`sidecar/` と `export/` も同じスナップショットに含める**。**動いたまま一貫したコピーが取れる。**
     - この 2 つを入れる理由: `sidecar/` は **PNG から取り直せない唯一のもの**（§5.1）で、`export/` は
       DB を失ったときの**最後の拠り所**（下の 3）。DB だけの写しでは、どちらも守れない。
   - **置き場は設定でき、既定は `<data>` の外**: `%USERPROFILE%\image-reviewer-backups\`（設定 `backup_dir`。
     環境変数 `IMAGE_REVIEWER_BACKUP_DIR` でも指定できる）。**理由**: `sidecar/` は `<data>` の中にしか無いので、
     バックアップも `<data>` の中に置くと**守るものが守られる対象の中に入る**（§5.1 の注記。`<data>` を失えば両方消える）。
   - 形は 1 日 1 フォルダ: `<backup_dir>/<YYYYMMDD>/` に `db.sqlite3`・`sidecar/`・`export/`・`manifest.json`。
   - 直近 7 個を残し、古いものを消す。
   - 画像を含まないので小さい（1 万枚で数 MB 〜 数十 MB。`sidecar/`・`export/` を足しても数 MB 増えるだけ）。
   - **旧既定の `<data>/backups/db-YYYYMMDD.sqlite3` は互換のために読むだけ**にし、新しいスナップショットは
     既定ではそこへ書かない（利用者が明示的に `<data>` の中を指定した場合はその指定に従う）。
     **未確認**: 旧いスナップショットを新しい置き場へ移すか、そのまま残すかは決めていない。

2. **明示的なバックアップ**
   ```
   image-reviewer backup --out <dir>            # DB スナップショット + export/ + sidecar/ + workflows/ + settings.json
   image-reviewer backup --out <dir> --include-library   # 取込モードの実体も含める
   ```
   - **既定で `sidecar/` と `export/` を含む**（PNG から取り直せないものと、最後の拠り所。日次のスナップショットと
     同じ理由）。`--out` の既定は日次と同じ（`backup_dir`）。
   - 既定で**画像とサムネイルを含めない**（参照モードでは画像は利用者のもの）。画像の実体を含めるのは
     `--include-library` を付けたときだけ（任意）。
   - `manifest.json` に版・件数・作った時刻・含めた範囲を書く（復元時に確かめる）。

3. **人間が読める書き出し**（`design.md` §6.2）
   - `<data>/export/review.json` は判断の内容を**人が読める形**で持つ。
     これは他ツール向けの契約であると同時に、DB を失ったときの**最後の拠り所**でもある。
     だから日次のスナップショットにも入れる。

4. **来歴の二重持ち**
   - 捕獲した英訳と生成パラメータは、DB と `<data>/sidecar/<sha256>.json` の**両方**に書く（§5.6）。
   - `sidecar/` の形は `design.md` §7.3.1 が起こりで、プロトタイプの `write_sidecar`
     （`src/image_reviewer/capture.py`）が既にこの形で書いている（§5.6）。
   - DB を失っても `image-reviewer rebuild-metadata` で PNG と sidecar から組み直せる。
     ただし **`<data>` ごと失えば sidecar も消える。** この対策が成り立つのは
     **`<data>` の外にバックアップがあるときだけ**である（§5.2 の 1）。
   - **点検で見つかった誤り（旧 §5.2 の書き方）**: 旧版は「日次スナップショットは DB だけを `<data>/backups/` に
     取る」とし、リスク 11 の対策を `<data>` の中だけで閉じていた。**「データ置き場を消したとき」に備える対策を、
     データ置き場の中に置く**のは論理が閉じていない（`review-report.md` の B3・E5）。

### 5.3 復元

```
image-reviewer restore <バックアップ先> [--force]
```

- `manifest.json` を読み、版と件数を出す。
- スナップショットに `sidecar/`・`export/` が入っていれば、それも `<data>` へ戻す
  （DB だけ戻すと、PNG から取り直せない来歴の種が欠ける。§5.2 の 1）。
- 既存の DB があるときは**先に自動バックアップを取ってから**置き換える。
- 置き換えた後、`PRAGMA integrity_check` を通す。通らなければ元に戻す。
- 復元後は走査を 1 回促す（参照切れを拾う）。

### 5.4 マイグレーション

- 版は `PRAGMA user_version` に持つ（DB のファイル名に依存しない）。
- **前方のみ**。起動時に「DB の版 > バイナリの版」なら**起動を拒否**して理由を出す
  （新しい DB を古いコードで壊さない）。
- 版を上げる前に自動バックアップを取り、失敗したら巻き戻す。
- マイグレーションは冪等に書く（途中で落ちても再実行できる）。

### 5.5 健全性

| いつ | 何を | 失敗したら |
| --- | --- | --- |
| 起動時 | `PRAGMA quick_check`（速い） | **読み取り専用で起動**し、復元を案内する。黙って書き込まない |
| 日次バックアップ時 | `PRAGMA integrity_check`（重い） | 利用者に知らせ、`<backup_dir>/` の古いスナップショットを残す |
| 復元後 | `PRAGMA integrity_check` | 元に戻す |

- WAL のチェックポイントは終了時と日次で行う（`PRAGMA wal_checkpoint(TRUNCATE)`）。
- `-wal` / `-shm` を**単独でコピーしない**（壊れた DB になる）。必ず online backup API を使う。

### 5.6 sidecar の形（`<data>/sidecar/<sha256>.json`）

捕獲した来歴を、**人間が読める JSON として 1 枚 1 ファイル**で持つ。プロトタイプの `write_sidecar`
（`src/image_reviewer/capture.py`）が既にこの形で書いている。**この文書はその形を設計として固定する**
（起こりは `design.md` §7.3.1）。

- **置き場と名前**: `<data>/sidecar/<sha256>.json`（内容のハッシュが名前）。同じ内容なら何度捕獲しても
  同じ 1 ファイルに上書きされる（`asset` が内容で 1 行なのと同じ。§1.1）。
- **鍵**:
  - `schema`: `"urn:image-reviewer:sidecar"`（この形であることの印）
  - `abi`: `"0.1"`（**このファイルの形の版**。DB の `user_version`（§5.4）とは別に持つ）
  - `captured_at`: 捕獲した時刻（UTC、`YYYY-MM-DDTHH:MM:SSZ`）
  - `sha256` / `path` / `prompt_id` / `captured_from_node`: どの内容の、どの実行の、どのノードから取ったか
  - `en_text`: **捕獲した英訳**（PNG から取り直せない唯一のもの。§5.1）
  - `final_prompt`: 連結を組み直した最終プロンプト。`ja_text`・`concat_prefix`・`concat_delimiter` も一緒に持つ
    （`rebuild-metadata` が組み直すのに要る）
  - `textgen_params` / `textgen_system_prompt` / `llm`: 訳を作った条件（再現の L1。`workflow-reproduction.md` §4.2）
  - `meta`: そのときの `asset.meta` の写し（捕獲の判断材料を後から見られるように）
- **書き方は原子的**: 同じフォルダに `<sha256>.json.tmp` を書いてから `os.replace` で置き換える
  （`store.json` と同じ）。書き込み中に落ちても**半分だけ書けた JSON を残さない**。
- **1 枚 1 ファイルにする理由**: 捕獲は生成の瞬間にしか起きないので、**その 1 枚の分だけを書き足せればよい**
  （DB 全体を書き直さない）。人間が読めるので、DB を失っても `rebuild-metadata` で組み直せる（§5.2 の 4）。
- **DB との関係**: 同じ内容を DB と sidecar の**両方**に持つ（二重持ち）。**正は DB、sidecar は再構築の種**。
  食い違ったときは DB を採る（**未確認**: 食い違いを検出して画面に出すかは決めていない）。
- **点検で見つかった誤り（実装）**: プロトタイプは捕獲の値を `store.json` に書くだけで、sidecar を
  **書いていなかった**。実データで捕獲できた 1 枚の英訳は `.data/store.json` にしか無かった。
  プロトタイプは `write_sidecar` を足して直した（`review-report.md` の I5）。この文書では上のように形を固定する。

## 6. 性能

| 操作 | 目標 | 根拠（実測 / 見積り） |
| --- | --- | --- |
| 初回走査 1 万枚（ハッシュ込み） | **90 秒以内** | ハッシュ 34 秒 ＋ PNG 解析 0.4 秒 ＋ 歩査と DB 書き込み（`design.md` §12.1。実測は `metadata-findings.md` §7） |
| 初回走査 1 万枚（`--no-hash`） | **30 秒以内** | 解析 0.4 秒 ＋ 歩査と DB 書き込み（`design.md` §12.1） |
| 2 回目以降の走査（差分なし） | 10 秒以内 | ハッシュを計算しない（`design.md` §12.1） |
| 完全重複の検出 | 100ms 以内 | `GROUP BY` 1 本 |
| 準重複の検出（1 万枚） | 2 秒以内 | 帯索引で候補を絞る（§2.2 の 8bit × 8 帯） |
| pHash の全件計算 | 2 分以内 | [`comparison.md`](comparison.md) §7 の**未計測の見積り**（8ms/枚）× 1 万枚。**実測ではない** |
| 日次バックアップ | 5 秒以内 | online backup API ＋ `sidecar/`・`export/` の写し。数十 MB（§5.2 の 1） |

**走査の 3 つの目標**（ハッシュ込み 90 秒 / `--no-hash` 30 秒 / 差分なし 10 秒）は
`design.md` §12.1 と**同じ値**である。この文書から新しい値を足さない。
`design.md` §12.1 の「内容ハッシュ 1 万枚 60 秒以内」は**ハッシュ計算だけ**の目標で、走査全体の目標ではない
（実測でハッシュが 34 秒かかるため）。旧版の「`design.md` §12.1 の『初回走査 60 秒』」という引用は
**§12.1 に存在しない行**を指していたので削除した。`--no-hash` は **30 秒以内**（旧版の 60 秒は誤り）。
pHash の 8ms/枚は**未計測の見積り**であり、実測として書かない（出所は `comparison.md` §7 1 か所）。

## 7. 決めていないこと

1. **ハッシュの方式。** 今の実装は SHA-256（実測 399 MB/s）。BLAKE3 なら数倍速いが、
   依存が増える（標準ライブラリで済む利点がある）。
   → **SHA-256 を推奨**。速度は足りている。
2. **pHash のしきい値。** 実データで決める（初期値 ≤ 6 / SSIM ≥ 0.95）。
3. **ゴミ箱の自動掃除を既定で ON にするか。** 今は「通知のみ」を既定にしている。
4. **取込モードの実体をバックアップに含めるか。** 既定 OFF（容量が大きい）。
5. **`asset` を持たない「未同定」の状態を作るか。** `--no-hash` を付けたときの扱い。
   今は「`--no-hash` は一覧の下見専用で、判断はできない」としている。判断を許すなら
   パス基準の暫定 ID が要る（複雑になるので勧めない）。
6. **保留領域の置き場所（対象が `<data>` と別ボリュームにあるとき）。** 既定は
   `<data>/pending-delete/`。別ボリュームの対象では**対象側に置く必要がある**が、命名と場所は**未確認**（§3.4）。
7. **旧い日次スナップショット（`<data>/backups/`）の移行。** 新しい置き場（既定は `<data>` の外）へ移すか、
   そのまま読めるように残すか。**未確認**（§5.2 の 1）。
8. **sidecar と DB が食い違ったときの見せ方。** 正は DB と決めた（§5.6）が、食い違いを検出して画面に出すかは
   決めていない。
9. **クラッシュで `remaining_sec` が 0 のまま残った行の猶予の見せ方。** 起動時には消さず、
   タイマーの最初の確認で消す（§3.4）。この 1 回の猶予を画面でどう見せるかは**未確認**。
