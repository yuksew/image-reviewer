## 2. この段は何か

`design.md` §14 の工程 **P6**。順序は **P1 → P2 → P3 → P5 → P6 → P4 → P7 → P8 → P9**（点検 G11 で確定）。
P6 は **要求（R10）と注記（R11）** を作る段です。

完了条件（`design.md` §14 の P6 の行）:

- エージェントが要求を投げ、**投げてすぐ返る**
- **要求の一覧から開いて判断し、判断で閉じる**
- **印を囲んでメモを付け、座標と切り出しを書き出せる**

**この段では作らない**: タグと語釈（P4）、条件の記録と再現（P7）、重複と削除（P8）、監視（P3）、
日次の全件書き出し、SSE（`GET /api/events`）。

## 3. すでに確定していて、覆せないこと

**これに反する設計は「矛盾」として指摘**してください。

**要求（R10。`design.md` §9.6 の決定表）**
- 経路は **HTTP API だけ**。ファイル監視などの別口は作らない
- **投げてすぐ返る**。エージェントは `GET /api/review-requests/{id}` を**ポーリング**して結果を得る
- 上書きは **同じ `target_key` の未対応の要求だけ**を `superseded` にして差し替える。
  **`target_key` が無ければ上書きしない**（別の要求として積む）
- 要求は**まとまり（`review_group`）を作る**。要求専用のレビュー画面を作らない
- AI の下書き（`ai_pick_asset_id` / `ai_note`）は**人が確定する**。自動でキープにしない
- 気づき方は上部バーの件数と**タブのタイトル**。音は使わない
- 断るときは**理由が要る**（`decline_note`）
- **エージェントは判断を書けない**（判断の口は `actor='human'` 以外 403）

**注記（R11。同 §9.7）**
- **矩形と楕円だけ**（自由曲線は作らない）。座標は **0〜1 の割合**
- 1 領域に 1 つのメモ。**領域なしの注記**（まとまり全体へのメモ）も同じ表で扱う
- 書き出しは**両方**: ①座標と文の JSON（エージェントが読む）②**囲んだ範囲ちょうどの切り出し画像**（余白を付けない）
- 人の注記とエージェントの注記を区別する（`actor`）。**両方出す**
- 注記は**判断の理由の代わりではない**（ボツの理由は理由マスタから選ぶ）

**契約（`schemas/review-export.schema.json`。**すでに P6 の形が入っている**）**
- `requests[]`（任意）＋ `ReviewRequest` / `ReviewRequestState`（`open` / `done` / `declined` / `superseded`）/
  `ReviewRequestResponse`（`selected_asset_ids` / `reason_code_id` / `reason_label` / `note` / `annotations`）
- `Annotation` / `AnnotationId`（`shape` / `x,y,w,h` / `body` / `actor` / `created_at` / `group_id`）
- `design.md` §16.2 の 9・10 で「要求の状態」と「画像の種別」を契約に入れると**決定済み**

## 4. とくに見てほしいこと

1. **`design.md` との整合。** §9.6 / §9.7 の決定表、§5.6 の表定義（`review_request` / `annotation`）、
   §6.1 の API 一覧、§6.2 の契約、§14 の完了条件、§16.2 の申し送り（9・10・11）、§19 の点検観点
   （とくに §19.2 の 6「`review_request` の上書きと画像の差し替えがエージェントから見て分かりやすいか」）。
   **設計が design.md を書き換えている場合、その差分（§0）が妥当か。**
2. **完了条件が「実行して確かめられる形」か。** P5 の監査 B16 は「確かめられない完了条件があると
   工程の規律が働かない」と指摘した。**数値・手順・合否の線**が書かれているか。
   書けないなら「確かめ方」が先に決まっているか。
3. **`GET` に副作用が無いか。** P5 では `GET /api/export/review.json?scope=all` がファイルを書いていて
   問題になった（監査 C8/G2）。**P6 の GET が状態を変えないか**（ポーリングの口が特に危ない）。
4. **再送と冪等。** P5 は「同じ `client_token` の再送は 200＋`superseded`」に確定した。
   P6 の受付・判断・注記に**同じ仕組みが要るか、要らないか**が書かれているか。
   `target_key` の上書きは**同じ要求を二度投げたときに増えないか**。
5. **`actor` の扱い。** 判断は `human` 以外 403。**注記は `agent` も書けるのか**（`annotation.actor` は
   `human` / `agent` を許す形になっている）。設計がどちらに決めたか、理由つきで書かれているか。
6. **状態遷移の網羅。** `open` → `done` / `declined` / `superseded` の**全経路**（判断で閉じる、
   断る、上書き、まとまりが消えた場合、対象の画像が消えた場合）が表で網羅されているか。
   **`superseded` の連鎖**（A を B が差し替え、B を C が差し替え）が壊れないか。
7. **切り出しの実装可能性。** 0〜1 の座標から**どの画素を切るか**（丸め、境界、最小 1 px）、
   **書き出し先の命名と原子性**、**失敗したときに何を失わないか**（P5 の `.tmp` の教訓）、
   **拡大縮小の扱い**（`thumb` か原本か）が決まっているか。
8. **画面。** 要求の一覧（`#/requests`）と注記の入口が `frontend-design.md` の**画面一覧・部品・文言と一致**するか。
   前回の点検 C13 は「**まとまりレビューの画面に注記の入口が無い**」「『保留』と『あとで』の語が揺れる」
   「『取り消す』が 2 つの意味に使われている」と指摘した。設計がこれを解いているか。
   **キーが無くてもマウスだけで完結するか**（P5 の原則）。
9. **テスト方針が「何を壊すと落ちるか」になっているか。** P5 の監査は「何も守っていないテスト」を
   実際に見つけた（F 節）。**守るテストの一覧**が書かれているか。
10. **工程の切り方。** 小段（P6-0 / P6-1 …）ごとの**合格の線**と、**Fable に監査させる単位**が
    書かれているか。1 段が大きすぎないか。
11. **未確認・リスク。** 実機で確かめていない前提を**推測で埋めていない**か。
    `design.md` §16.2 の申し送りのうち P6 に関わるものを拾っているか。
12. **設計者が依頼者に投げた 3 つの選択**（設計は下記を推奨している。**あなたの意見**を `G` に書いてください）:
    - **(a) 切り出しの書き出しを `GET` で受けるか。** (i) `GET` は `format=json` だけにして `format=crops` は
      **422 で `POST` を案内**（設計の推奨。P5 の「`GET` は書かない」に揃える）／(ii) `GET` でも書く
      （`design.md` §6.1 の字面どおり）／(iii) `GET` はその場で作って返すだけで**ファイルを残さない**。
    - **(b) 要求の応答を保存するか導出するか。** (i) **閉じた時点の写しを `response` 列に保存**（設計の推奨。

## 5. 報告の形式

`docs/p6-review-report.md` に:

```markdown
# P6 設計の点検報告

- 点検した版 / **実行できたかどうか（実行したコマンドと結果）**
- 総合判定: このまま実装してよい / 直してから実装 / 作り直す

## A. 設計の主張が成り立たない（必ず直す）
## B. 重大（実装すると静かに壊れる・後で直すと高い）
## C. 中程度
## D. 軽微
## E. design.md とのずれ（設計が design.md を書き換えている場合はその妥当性）
## F. テストで守れないもの
## G. 依頼者への質問（**利用者が決めること**。選択肢と推奨つき）
## H. 確かめられなかったこと
```

- 各項目に**必ず「場所」**（`docs/p6-design.md` の節・行）と、**根拠**（実行したコマンド、または design.md の行）。
- **問題が無いと確認した観点は 1 行**で「確かめた結果、問題なし」。
- 最後に**最も重大な 3 件**を理由 2〜3 文で。
