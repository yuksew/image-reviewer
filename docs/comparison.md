# 比較の設計

要件の「画像を保存・**比較**・レビュー」のうち、比較の部分を詰める。
比較は独立した機能ではなく、**まとまりのレビュー（`design.md` §9.3）の中身**である。
「8 枚を見比べて 1 枚選ぶ」という 1 つの作業を、3 つの見方で支える。

- 版: 0.1（実装前）
- 前提: [`metadata-findings.md`](metadata-findings.md)、[`design.md`](design.md) §7（来歴）・§12（性能）

---

## 1. 比較の 3 つの見方

| 見方 | 何を比べるか | いつ効くか | 実装の重さ |
| --- | --- | --- | --- |
| **A. 見た目** | 画素 | 構図・表情・手の形・塗り | 中（ビューアと位置合わせ） |
| **B. 来歴** | seed / steps / cfg / モデル / LoRA / プロンプト / タグ | 「何が違うから違うのか」を知りたいとき | **軽い（一番効く）** |
| **C. 機械の指標** | 知覚ハッシュ・SSIM・色 | 似ている順に並べる、重複を見つける、再現を検証する | 中（numpy で完結） |

**既定は B を出す。** 生成を回す現場では「seed だけ違う」「LoRA を足した」「steps を半分にした」が
判断の材料になる。画素の比較はそれを見てからでよい。

**点数（星 1〜5）は入れない。** 条件ごとの ○/× を採る。「30 枚を回して選別する」現場では
**何が違うかを一覧で見る**方が速く、点数は後から見て「なぜそう判断したか」が残らないからである。

今回作る見方は 5 つ: **並べる / 来歴の差分表 / 差分ヒートマップ / 同期ズーム・パン / 似ている順に並べる**。
点滅・スワイプ・重ねるは今回作らず、後から足せる形だけ用意する（§9）。

> **参考にした既存実装（連携はしない）**: 別プロジェクト `illust-authoring` を**読み取り専用**で眺め、
> 点数ではなく条件ごとの ○/× を採る形を参考にした。このツールは同プロジェクトとコードもデータも共有せず、
> 呼び出し・取込・書き戻しのいずれの連携もしない（今後の予定も無い）。以下の設計はすべて
> このツール単独の判断として書いてある。

## 2. A. 見た目の比較

### 2.1 並べる（既定）

- 2〜8 枚を 1 画面に並べる。枚数で自動レイアウト:

| 枚数 | レイアウト |
| --- | --- |
| 2 | 左右 2 列 |
| 3〜4 | 2 × 2 |
| 5〜6 | 3 × 2 |
| 7〜8 | 4 × 2 |

- **1 行に入る枚数は窓の大きさ（と絵の縦横比）で決まる。** 上の表は「**1 画面に収める**」ための
  目安で、**枚数ごとの行数を強制はしない**（強制すると、窓が狭いときに縦へ溢れてスクロールになる）。
  実装は、枠の高さを「舞台の高さ ÷ その枚数の行数」で決め、幅は絵の縦横比に従って
  **入るだけ並べて折り返す**。したがって窓が広いほど 1 行に多く並ぶ。
- 監査 B1（実行込みのやり直し）の修正: `renderDiff()` → `renderStage()` の順に描き（表を先に
  入れて舞台の高さを確定させる）、枠の高さは**見出し（`.cmp-cap`）と行間も引いて**決め、
  **タイルの幅も枠に合わせる**（見出しは `nowrap` なので、揃えないと見出しの幅 309〜434px が
  タイルを広げ、幅の見積りが当たらない）。見出しは**省略表示でよい**（枠の中で `…` に切れる）。
- 実測（`node tools/gui_layout.mjs --base <url> --count 8`。3 窓 ×（初回・`resize` 後・`r` 後））:
  **どの窓でも舞台の外に出るタイルは 0**、タイル幅＝枠幅（1400×900 で 162px、1200×800 で 135px、
  1920×1080 で 210px）。**8 枚はどの窓でも 1 行**に収まり、**舞台の縦は約 50% だけ使う**
  （正方形 8 枚を幅いっぱいに並べると、その高さは舞台の半分で足りるため）。見出しの可視は
  27〜45%（モデル名までで、`seed`/`steps`/`cfg` は切れる）。この「下が空く」状態は
  **縦の余裕を増やさない限り避けられない**（舞台を高くするか、差分表を畳むかが選択肢）。

- 各タイルの下に **seed・steps・cfg・モデル名（短縮）** を 1 行で出す。
  seed が同じ組には「同一 seed」バッジを出す（後述 §3.3）。
- 拡大は **1024 サムネ**を使う（原本は開かない）。8 枚でも 8MB 程度で、`design.md` §12 の目標内に収まる。
- タイルの左上に**順位（1〜8）**を出し、キー番号と対応させる。

### 2.2 同期ズーム / 同期パン

差分を見る基本動作。**1 枚を操作すると全部が追従する。**

- ホイールでポインタ位置を中心に拡大（0.5x〜8x）。`+` / `-` / `0`（等倍）。
- ドラッグまたは `Space` + ドラッグでパン。
- `z` で同期の on/off。off にすると 1 枚だけ動かせる（「ここだけ見たい」とき）。
- 実装: 各タイルの `<img>` に同じ `transform: translate(...) scale(...)` を当てる。
  再描画しない（`will-change: transform`）。8 枚でも 60fps。

### 2.3 位置合わせ（registration）と差分ヒートマップ

**すべての画像で差分を出すのではない。** seed が違えば画素はほぼ全部違うので、ヒートマップは無意味になる。
差分ヒートマップを**自動で**出すのは次の 2 つの場合だけ（判定はサーバ。使えない組はボタンを無効にし、
**理由を 1 行で出す**）:

- 同じ seed（`provenance.seed` が一致）
- 知覚ハッシュ距離が `HEATMAP_DISTANCE_THRESHOLD`（= `PHASH_NEAR_THRESHOLD`。**6**）以下（近い画像）

- **「派生関係」（`external_ref` / `regenerated_from`）の条件は外してある。** 以前はこれを 3 番目の条件として
  書いていたが、**その関係を持つ列がまだ無い**ので P7 まで外す（無い列で判定した気になるのを避ける。点検 G6）。
- 条件の外でも、利用者が明示的に「差分を見る」を押せば出せる（`force`。点検 G6）。

**同じ seed は「同じ絵」を意味しない。** 位置合わせの判別は「合わせた重なりの一致度」
（`ALIGN_MIN_CORR = 0.80`）で行い、**下回る組は画像を返さず**「位置が合いません」と言う。
実測（[`p5-design.md`](p5-design.md) §0.7。実データ 263 枚）: 無関係な 200 組の一致度は最大 **0.758**、
同じ絵の縮小・再圧縮は **0.949**、ずらした写しは **1.000** で、**0.80 はこの間**にある。
峰の比（`max / mean(|corr|)`）は判別に使えない（無関係が p50 **5.66** / 最大 **71.8**、同じ seed が
**5.14〜216.3** で範囲が重なる）。そのため**同じ seed でも絵が実際に違えば「位置が合いません」を返し、
でっち上げたヒートマップを出さない**（実測では同じ seed の 49 組のうち一致度 0.80 を超えたのは 3 組だけ）。

**追記（監査 C1・実行込みのやり直し）**: 実装は峰の比も**補助の門**として使っている
（`peak_ratio ≥ 8.0` **かつ** `corr ≥ 0.80`）。実行での実測では、無関係な 60 組の峰の比は
min 4.94 / p50 5.70 / max **15.00**、一致度は max **0.555** で、**「合わせた」と言った組は 0**
（峰の比だけで落ちるのは 2 組、残りは一致度が落とす）。同じ seed の 85 組では**そろうのは 4 組だけ**
（一致度 0.814〜0.983）で、残り 81 組は「位置が合いません」になる。**つまり「同じ seed」は
「合う」の予測ではない**（この 19 の seed には、違うプロンプトの絵が 2〜31 枚ずつぶら下がっている）。
だから画面では**言い切らない**: 「差分: 同じ seed の組です（合うかは出してみるまで分かりません）」と出し、
**「強制して出す」は常に見えるようにする**（以前は条件を満たす組では隠していた）。

手順:

1. 両方を 256px の長辺へ縮小（アスペクトは合わせる）。
2. **平行移動だけ**を位相相関（numpy の FFT）で推定し、ずれを補正する。
   - 回転・拡大は**扱わない**と決める。生成画像の比較で回転ずれは稀で、
     対応すると実装と UI が一気に重くなる。ずれが大きいときは「位置が合いません」と出す（黙って誤魔化さない）。
3. グレースケールの絶対差 → **3 倍に増幅して**赤で元画像に重ねる。
   **この増幅は表示だけ**で、下の差の 2 つの指標（`changed_fraction` / `mean_abs`）には影響しない
   （指標は増幅前の差で計算する）。
4. 併せて数値を出す: **SSIM**（`ssim`）・**変化した画素の割合**（`changed_fraction`）・**平均絶対差**（`mean_abs`）。
   **指標は手順 1 の縮小（＝位置合わせ前）の 2 枚から計算し、手順 2 は表示の絵だけに掛ける。**
   以前は「手順 1 と 3 の差」と書いていたが、間に手順 2（位置合わせ）が入るので**誤り**。
   ずれは差として数える——そうでないと、絵を**ずらしただけ**で「同じ」に見えてしまう。
   指標は**再現の検証**と**準重複の確定**に使う（§4 の表）ので、位置合わせの成否に依存させない
   （合わない組でも数値は返る）。
   定義は §4 に**1 回だけ**書く（**このツールの契約**として固定し、他の文書はそこを参照する）。
   同じ定義を**再現の検証**（[`workflow-reproduction.md`](workflow-reproduction.md)）でも使う。

## 3. B. 来歴の比較

### 3.1 表の作り方

- 比較する画像群の来歴キーの**和集合**を取り、1 行 1 項目の表にする。
- 行は「違う行」を上に、「同じ行」を畳んで下に置く（`m` で展開）。

```
項目            1          2          3          4
seed            338134650  338134650  998211003  998211003      ← 同じ値は同色
steps           10         10         20    ↑    20
cfg             1.0        1.0        1.0        1.0            （畳み）
LoRA            —          BuAnimeV2  —          BuAnimeV2
positive        1girl, ... 1girl, ... 1girl,...  1girl,...
```

- 差分の強調: 変わった値だけ太字と色。数値は**増減が分かる形**で出す（`steps 10 → 20`）。
- 2 枚の比較では表ではなく**左右 2 列の diff 表示**にする（片側に `−`、片側に `+`）。

### 3.2 プロンプトの差分

- 正規化は**2 段**に分ける（点検 G5 で修正。以前は「重みの表記も同一視する」と書いていたが、**誤り**）。
  - **段 1 = 語の同定**（同じ語と見なすための正規化）
    - 末尾のカンマ・空白・改行
    - 大文字小文字
    - `_` と空白（Danbooru のアンダースコア表記）
  - **段 2 = 値の比較**（重みは**同一視しない**）
    - `(word:1.2)` と `word` は**同じではない**。重みは絵を変えるので、**重みだけが違う語は
      `reweighted`** として差に出す（`same` に潰すと「何が違うから違うのか」が消える）
    - `((word))` の段数（1.1 の冪）と `<lora:name:0.8>` の強さも同じ扱い
  - **語順だけの違いは `moved`**。追加と削除に割らない（同じ語が両側に出て読みにくくなる）
  - 語の順（順序だけの違いは「移動」として扱い、追加・削除と区別する）
- 差分は**語単位の LCS**。追加=緑、削除=赤、移動=灰色。
- 日本語原文は語の切り分けが難しいので、**文単位 → 文字単位**の 2 段で差分を取る。
- 正規化しても差が残る場合だけ強調する（正規化前の生の文字列も折りたたんで併記する）。

### 3.3 「同一 seed」の扱い

同じ seed で他が違う画像は、**同じノイズから出発している**ので比較の意味が強い。
このツールの既定も**同じ seed で比べる**ことにし、次のように扱う。

- seed が同じ組には「同一 seed」バッジを出し、**その組を既定の比較対象にする**。
- seed が全部違う組では、「seed が違うので画素は別物」と 1 行で明示する
  （差分ヒートマップを使えない理由でもある）。

### 3.4 タグの差分

- 出所（`png` / `wd14` / `manual`）ごとに、**A だけ / B だけ / 両方**を並べる。
- `wd14` はスコアも出す。「0.98 と 0.41 で同じ `1girl`」は判断の材料になる。
- カテゴリ（general / character / copyright）でまとめる。

## 4. C. 機械の指標

同じ計算を**3 か所で共有する**（重複検出・比較の並べ替え・再現の検証）。1 回実装して 3 度使う。

| 指標 | 何を表すか | 実装 | 使う所 |
| --- | --- | --- | --- |
| **pHash**（64bit） | 構図・大きな明暗の配置 | 32×32 グレースケール → DCT → 低周波 8×8 → 中央値で 2 値化 | 重複候補、似ている順の並べ替え、再現の検証 |
| **dHash**（64bit） | 勾配（線・輪郭） | 9×8 グレースケール → 横方向の増減 | pHash の補助 |
| **SSIM** | 見た目の一致度（0〜1） | 256px へ縮小 → 局所平均・分散・共分散 | 再現の検証、準重複の確定 |
| **色ヒストグラム距離** | 塗り・色調の違い | 各チャンネル 32 ビン、L1 距離 | 塗りの違い（セル調 / 写実寄り）を見る |

- ハッシュ類似度 = `1 - hamming / 64`。
- しきい値の初期値: pHash 距離 **≤ 6** を「近い」、SSIM **≥ 0.95** を「ほぼ同一」。
  **この 2 つの数値は実データで必ず調整する**（`design.md` §16 に「実測で決める」として残す）。
  根拠なく固定すると、重複の誤検出と見落としの両方が出る。
- 塗りの違いは、色調が系統的に変わる条件（例: 昼の屋外＝セル調 / 夜のランプの室内＝写実寄り）を
  拾うための指標として置く。**実データでの効き方は未確認**なので、しきい値と併せて調整する。

**差分の 2 つの指標（定義の正はここ。他の文書はここを参照する）**

同じ 2 枚を比べたときに出す数値。どちらも **256px の長辺へ縮小したグレースケール**（§2.3 の手順 1・3）で、
**増幅前の絶対差（0〜255）**から計算する。赤く重ねるときの **3 倍増幅は表示だけ**で、この 2 つの値には影響しない。

| 名前 | 定義 | 範囲 |
| --- | --- | --- |
| `changed_fraction` | **絶対差が 8 を超えた画素の割合**（`abs(a - b) > 8` の画素数 ÷ 全画素数）。閾値 **8 は増幅前**の差に当てる | 0〜1 |
| `mean_abs` | **増幅前の平均絶対差**（`mean(abs(a - b))`） | 0〜255 |

- この定義が**文書間の正**。他の文書（[`workflow-reproduction.md`](workflow-reproduction.md)・
  [`duplicates-deletion-backup.md`](duplicates-deletion-backup.md) など）はここを参照し、
  **別の閾値や「増幅後」の定義を書かない**。
- 単位: `changed_fraction` は割合（0〜1）、`mean_abs` は 8bit の階調差（0〜255）。

### 4.1 似ている順に並べる

- 1 枚を基準に、他を pHash 距離の昇順に並べる。「この絵に似た絵」を探す。
- 8 枚の比較では並び順を「入力順 / seed 順 / 基準に似ている順」で切り替えられる（`r` キー）。

## 5. まとまりの種類ごとに、どの見方を使うか

| まとまりの種類 | 主に使う見方 | 画面の既定 |
| --- | --- | --- |
| 同じプロンプトの seed 違い（候補群） | B（seed だけ違う）→ A（並べる・差分） | 並べ + 来歴の差分表 |
| 差分生成（variation） | A（差分ヒートマップ）→ B（差分の種類） | 並べ + 差分ヒートマップ |
| 仕上げの前後（postprocess） | A（差分ヒートマップ） | 差分ヒートマップ |
| モデル / LoRA の比較 | B（モデル・LoRA）+ C（色） | 並べ + 来歴の差分表 |
| 再現の検証（[`workflow-reproduction.md`](workflow-reproduction.md)） | C（SSIM・pHash）+ A（差分） | 検証結果の 1 行 + 差分 |
| 重複の整理（[`duplicates-deletion-backup.md`](duplicates-deletion-backup.md)） | C（pHash）+ A（並べ） | 距離順の並べ |

## 6. 操作（キーボード。補助）

**キーボードは補助**（あればよい）。**キーが無いとできない操作は作らない**（すべてマウスだけで完結する）。
速く回したい人が使う。

| キー | 動作 |
| --- | --- |
| `1`〜`8` | そのタイルを選ぶ（選ぶと同時に拡大の対象にもなる）。**番号は常に「画面の並び」**（`r` で並びを変えても、押した番号のタイルが選ばれる。監査 C2。以前はサーバの並びで引いていたので、似ている順では `3` を押すと番号 4 が選ばれ、語の差分の「2 番」も表の 2 列目と別の枚を指していた） |
| `Tab` / `Shift+Tab` | 次のタイル / 前のタイル |
| `g` | 並べ（既定） |
| `d` | 差分ヒートマップ（使えない組では無効） |
| `b` | 差分の「基準」に固定 |
| `z` | 同期ズームの on/off |
| `+` / `-` / `0` | 倍率 / 等倍 |
| `r` | 並び順の切り替え |
| `m` | 来歴表の「同じ行」を展開・畳む |
| `Enter` | 選択中のタイルをキープ（まとまりから選ぶ） |
| `x` | 選択中のタイルをボツ |
| `A` | すべてボツ |
| `Esc` | 比較を閉じる |

`f` / `s` / `o` は §9 の見方のために**予約**しておく（今回は使わない）。

- まとまりごとボツにするときも、**理由は利用者が選ぶ**。`design.md` §9.2 の理由マスタのどれでも選べる。
  「同じまとまりにもっと良いものがある」のような特定の理由を**既定にしない**
  （まとまりの中の 1 枚を選ぶ操作と、まとまり全部を落とす操作は別の判断である）。

`design.md` §9.3 のまとまりレビューと同じキー割り当てにする（画面をまたいで覚え直さない）。

## 7. 性能

| 操作 | 目標 | 根拠 |
| --- | --- | --- |
| 8 枚の並べ表示 | 400ms 以内（サムネ生成済み） | 1024 サムネ 8 枚 ≒ 8MB。`design.md` §12 |
| 同期ズームの操作 | 60fps | `transform` のみ。再描画なし |
| 差分ヒートマップ | 10ms 以内（**256px の numpy の部分だけ**。復号を含めない） | **実測**（P5-3 の実行込み監査。`probe_heat.py` の中央値）: 原本 → 256 gray が **2048² 39.7ms / 1024² 12.0ms**、256 サムネ → gray が **1.53ms**、numpy だけ（位相相関＋差＋WebP）が **14.1ms**、1 組（1024²）で **38.2ms**、2048² の組は**約 94ms**。**費用は原本の復号が支配**（256 のサムネイルを入力にすればどの画素数でも 17ms 程度）。**WebP の符号化が 14ms の大半**（`method=4`。下げる余地あり） |
| 来歴の差分表 | 30ms 以内 | DB の行を突き合わせるだけ。画像を開かない |
| pHash の計算 | 8ms/枚（**未計測の見積り**。実測ではない） | 登録時に背景で。1 万枚で約 80 秒（この見積りからの計算）。**この値の出所はこの行 1 か所**。他の文書はここを参照し、実測として書かない |
| 似ている順の並べ替え | 100ms 以内（1 万枚） | uint64 の XOR + popcount を numpy で一括 |

- **SSIM 単体の目標は未定義。** 以前の監査（点検 E3）が「§7 に SSIM の行が無い」と指摘したままである。
  `p5-design.md` §8 の「SSIM（1 組）50ms 以内」はこの表の**ヒートマップの 50ms を借りたもので、出所が誤り**
  （[`p5-3-audit-report.md`](p5-3-audit-report.md) §E）。数字を発明せず、**未定義のまま**にする。
  実測の 26ms / 83ms は 1 組の処理の値で、**その大半は 2 枚の原本の復号**（1 枚 11.4ms）である。
- **比較は原本を復号する。** 以前は「比較のために原本を開かない」と書いていたが、**誤り**——実装は 256px の
  縮小を作るのに原本を開く（だから上の実測は復号込みで、**原本の画素数に比例**する）。復号済みの画像から
  ハッシュだけなら 2.38ms/枚、復号＋両ハッシュで 14.1ms/枚（[`p5-design.md`](p5-design.md) §0.7）。
  256 のサムネイル（既に縮小済み）を入力にする案は同 §0.7 に残っている。
- pHash は登録時の背景ジョブで計算し、`asset.phash` に保存する。**保存の型（16 進の TEXT）は
  [`duplicates-deletion-backup.md`](duplicates-deletion-backup.md) §1.3 が持つ**（符号なし 64bit は
  SQLite の符号付き `INTEGER` に入らないため）。

## 8. やらないと決めること

過剰設計を避けるため、明示的に落とす。

1. **回転・拡大を含む位置合わせ。** 平行移動だけ。生成画像の比較で必要になった実例が出てから考える。
2. **AI による美的評価（点数付け）。** 点数は判断の理由にならない。判断は人の ○/× と理由で残す。
3. **画像の類似検索のための埋め込みモデル（CLIP 等）。** 数千枚なら pHash で足りる。
   必要になったら `design.md` §16 に追加する。
4. **動画の比較。** 対象は静止画（`design.md` の要件どおり）。
5. **比較の結果を自動でキープにする。** 比較は材料を出すだけ。決めるのは人。

## 9. 後から足す（今回は実装しない）

次の 3 つの見方は**今回作らない**。利用者が選んだのは §1 の 5 つだけである。
ただし「どれも後から足せるようにする」と決めたので、足すときの形だけ先に決めておく。

足すときの拡張点:

- 見方を**モード登録表**（`mode_id` → 表示関数・入り口）に 1 行足す形にする。
  画面本体はモードを知らず、`g`（並べ）と同じ枠に差し込む。**既存モードのコードは触らない。**
- モードは**比較対象の来歴の配列（2〜8 枚）**だけを受け取る。DB・走査・判断の書き込みには触らせない。
- 位置合わせ（§2.3）は共通の下請けとして呼べるようにしておく（点滅とスワイプが使う）。
- キーは `f` / `s` / `o` を**予約**として空けておく（§6 の表には出さない）。

### 9.1 点滅（flicker）

2 枚を同じ位置で高速に切り替える。位置と構図の差が「動いて」見える。

- 既定 4Hz。`[` / `]` で 1〜10Hz。
- 事前に**位置合わせ**（§2.3）を行ってから点滅させる。ずれたままだと全体が揺れて何も見えない。
- 3 枚以上のときは「選択中 1 枚 vs 基準 1 枚」の 2 枚で行う（基準を指定する）。

### 9.2 スワイプ（split）

- 縦の分割線をドラッグ（または `←` / `→`）。線の左が A、右が B。
- 差分生成や仕上げの前後を確かめるのに最も向く。
- 分割線の位置は URL に残さない（一時的な見方）。

### 9.3 重ねる（overlay）

- A と B を重ね、不透明度を 0〜100% 動かす（ホイールは倍率に使うので、`Shift` + ホイール）。
- 「同じ構図で塗りだけ違う」を見るときに使う。
