## I. §11 の 12 の問いへの回答

1. **§2.1 の写しの規則** — 問題あり。ずれの経路は 3 つ。(a) 「最後」を `created_at` で決めると時計の逆行で誤る（C11）。(b) JSON ストアでは `cli scan` の `save()` が別プロセスの写しを丸ごと上書きする（B5-(a)）。(c) 起動時の組み直しが (a) の誤りを**正**として固定する。挿入順で「最後」を決め、台帳の書き手を 1 プロセスに限れば閉じる。`clear` で理由・日時を NULL に戻す規則そのものは問題なし。
2. **§3.2 の規則の過不足** — 問題あり。不足: `applies_to` の検査（C12）、`decided` への再 `decide` の応答（C3）、`items` の重複、`policy` の入口（C2）。利用者の手間: `pick_one` で 8 枚なら**7 回理由を選ぶ**のは `design.md` §9.2 の決定どおりで、設計の問題ではない。ただし「後から直せる」が reopen を引き起こす（B4）ので、直す経路を先に決めないと、利用者は「7 回選ぶ」か「直して未決定に戻る」かの二択になる。
3. **§3.1 のボツ理由必須** — 問題なし（決定どおり。「その他」が逃げ道）。速さの対策として「直前に使った理由を**選択肢の先頭に**出す（既定で選ばれてはいない）」を勧める。自動で付けないので §9.2 と矛盾しない。必須を外すと §9.2 と矛盾するので外さない。
4. **§4 の書き込みの道筋** — 問題あり。3 つは互いに矛盾しないが、**遅延中に落ちたときの判定が足りない**（B1 の 4 経路）。`created_at > mtime` を捨て、`review_group.changed_at` / `exported_at` で判定する。SSE はプロトタイプに無い（C16）。
5. **§3.4 の書き出しの範囲** — 問題あり。「影響したまとまり」の定義が無く、1 枚の判断は属する**全**まとまりのファイルを変える（B2）。どのまとまりにも属さない画像はどのファイルにも出ない（G11）。

7. **§7 のテスト** — 問題あり。今すぐ要るのに無いもの 14 件（C15。とくに「落ちても漏れない」「再送しても増えない」は設計の主張なのに 0 件）。要らないもの: 23 の絶対値、25・26 を合格の線に数えること。
8. **§8 の性能目標** — 100ms は SQLite なら達成の見込みがある（1 トランザクションに N+1 行）。JSON のままなら 263 枚では通るが、1 万枚では約 23 MB の書き直しになり（E8）、見込みが立たない。書き出しの遅延 2 秒は妥当だが、遅延の中身（まとめ方・実行時に読み直す）を書く（D10）。pHash 8ms は未計測のまま（F5）。SSIM 50ms の出所が誤り（E3）。
9. **手動タグを P4 に回す判断** — 問題なし。ただし `tags: []` は「無い」と読まれる（D5）。`null`（未計算）にする。
10. **§5 と `design.md` §9.3 の食い違い** — 問題あり（軽微）。「保留」が無い（C14-(3)）。各枚の下のパラメータ 1 行が無い（D8）。参照切れの印が無い（D7）。9 枚以上の送りにマウスの経路が書かれていない（D12）。

## 最も重大な 3 件

### 1. 書き出しの規則が、今の契約と組み合わせると壊れたファイルか古いファイルを出す（B1・B2・B3）

「影響したまとまり」が定義されておらず、1 枚の判断が属する全まとまりのファイルを変えることが見落とされている。`open` なまとまりのファイルは契約の `GroupItem.verdict` が null を許さないので書けない。落ちたときの判定は競合・秒の粒度・時計・reopen の 4 経路で漏れる。他ツールが読む唯一の口がこれなので、P5 の価値（R5c）が最初の実装で崩れる。著者は §11-4・§11-5 で遅延と範囲を問うているが、契約との衝突（B3）と reopen の漏れ（B1-(d)）には気づいていない。

### 2. 「後から直せる」が「decided を open に戻す」規則に当たる（B4）

全部ボツで写した理由を 1 枚だけ直す操作は、追記のみの台帳では同じ枚への `reject` の再追記になり、§4 の規則がまとまりを未決定に戻す。利用者には「直しただけで決定が消えた」と見える。逆に規則を `decide` だけに絞ると、選ばれた枚を単独でボツにした後も契約ファイルは「選ばれた」と言い続ける。結論が変わるときだけ戻す、と定義し直せば両立する。著者は §11-2 で「手間」を問うているが、この衝突には気づいていない。

### 3. 設計は SQL、実装先は JSON、しかも JSON には判断を失う経路がある（B5・C1）

P5 設計の §2・§4・§7 は SQLite が無いと書けない。一方プロトタイプの JSON ストアは、別プロセスの `scan` が `save()` で判断を丸ごと上書きし、同時要求が一時ファイルを取り合う。台帳は失ってはならないものの筆頭なので、そこに置いたまま P5 を始めてはいけない。P5 の最初に SQLite 化（機能を足さない）を置くのが、総費用が最も小さい。著者は §11-12 で JSON の重さを問うているが、上書きと競合の経路、および `design.md` §14 の着手順との食い違い（E1）には気づいていない。
